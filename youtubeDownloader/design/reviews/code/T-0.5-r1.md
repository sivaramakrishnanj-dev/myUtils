## C1 — `call()` bypasses CommandLine's configured output writer

- **Location:** `yt-cli/src/main/java/com/srk/myutils/yd/cli/Cli.java:20`
- **Severity:** Minor
- **Category:** Correctness
- **Spec citation:** —
- **Reviewer comment:**
  `call()` creates a **new** `CommandLine(this)` and writes to `System.out` directly: `new CommandLine(this).usage(System.out)`. This bypasses the `CommandLine` instance that picocli used to invoke `call()`, meaning any output writer configured via `cmd.setOut(...)` (as the tests do) is ignored for the no-args path. The tester's `execute_givenNoArgs_exitsZero` test passes only because it asserts exit code, not output content. This is a latent correctness issue — if a future test asserts on no-args output, it will fail unexpectedly.

  The idiomatic picocli pattern is to inject `@Spec CommandLine.Model.CommandSpec spec` and use `spec.commandLine().usage(spec.commandLine().getOut())`. However, since `call()` is a placeholder that will be entirely rewritten in T-1.11 (URL positional + flag parsing), this is Minor, not Major.
- **Suggested fix:**
  Replace the body of `call()` with:
  ```java
  @CommandLine.Spec
  CommandLine.Model.CommandSpec spec;

  @Override
  public Integer call() {
      spec.commandLine().usage(spec.commandLine().getOut());
      return 0;
  }
  ```
  Or accept as-is since T-1.11 rewrites `call()` entirely.

## C2 — Hard-coded version string will drift from pom.xml

- **Location:** `yt-cli/src/main/java/com/srk/myutils/yd/cli/Cli.java:15`
- **Severity:** Nit
- **Category:** Readability
- **Spec citation:** M0 gate: `--version` prints `youtube-downloader 1.0.0`
- **Reviewer comment:**
  The `@Command(version = {"youtube-downloader 1.0.0"})` literal duplicates the version from `pom.xml` (`<version>1.0.0</version>`). Today they match. On a future version bump, one could be updated without the other. A `@VersionProvider` reading from the jar manifest (populated by `maven-shade-plugin`'s `ManifestResourceTransformer`) would be the single-source-of-truth approach (*Effective Java* item 1 — static factory / provider over literal).

  For M0 this is fine — the literal is simple, correct, and the tool is pre-1.0 release. Flagging as Nit so it's on the radar for M5 polish (T-5.1 or T-5.6).
- **Suggested fix:**
  No action required now. Consider a `ManifestVersionProvider` in M5.

## C3 — No-args test does not assert output content

- **Location:** `yt-cli/src/test/java/com/srk/myutils/yd/cli/CliTest.java:52`
- **Severity:** Nit
- **Category:** Testing
- **Spec citation:** —
- **Reviewer comment:**
  `execute_givenNoArgs_exitsZero` asserts only `exitCode == 0` but does not verify that help/usage text is printed. This is partly a consequence of C1 (the output goes to real `System.out`, not the captured writer). If C1 is fixed, this test could also assert `stdout.toString().contains("Usage:")` for completeness. As-is, the test is still valuable — it confirms the exit code contract. Nit because the no-args behavior is a temporary M0 placeholder.
- **Suggested fix:**
  If C1 is addressed, add `assertThat(stdout.toString()).contains("Usage:");` to this test.
