## C1 — Surefire excludes @Tag("integration") by default

- **Location:** `pom.xml:131–137` — `maven-surefire-plugin` in `pluginManagement`
- **Severity:** Praise
- **Category:** Correctness
- **Spec citation:** AC-11.3 — "The test suite SHALL fail its default run (`mvn test`) if any unit test makes a network call. Network access in tests is enabled only in a separate, explicitly-named integration profile (`mvn verify -P integration`)."
- **Reviewer comment:**
  Correct use of `<excludedGroups>integration</excludedGroups>` in Surefire's default configuration. This ensures `mvn test` and `mvn verify` (without `-P integration`) will never run `@Tag("integration")` tests. Verified via `mvn help:effective-pom` — the exclusion propagates to both child modules without any child-level override.

## C2 — Failsafe executions gated behind profile — Maven-idiomatic

- **Location:** `pom.xml:138–144` (pluginManagement) + `pom.xml:150–167` (profile)
- **Severity:** Praise
- **Category:** Correctness
- **Spec citation:** AC-11.3
- **Reviewer comment:**
  The implementer correctly placed Failsafe's version + `<groups>integration</groups>` in `pluginManagement` (no executions), and added the `integration-test` + `verify` goal executions only inside the `<profile id="integration">` block. This is the Maven-idiomatic pattern: without `-P integration`, Failsafe is declared but never bound to any lifecycle phase, so integration tests are completely inert. Confirmed via effective-POM comparison with and without the profile. This answers the tester's question affirmatively.

## C3 — Version lockstep between Surefire and Failsafe

- **Location:** `pom.xml:33` — `<surefire-failsafe.version>3.5.5</surefire-failsafe.version>`
- **Severity:** Praise
- **Category:** Reliability
- **Reviewer comment:**
  Both plugins share a single version property (`surefire-failsafe.version`), guaranteeing lockstep upgrades. This avoids the subtle class-loading and provider-mismatch bugs that occur when Surefire and Failsafe drift to different versions. Clean practice per Maven plugin hygiene. (Effective Java item 1 spirit — single source of truth for a shared constant.)

## Tester question — addressed

> "Failsafe in pluginManagement has no `<executions>` by default; executions are added by the integration profile. Tester asks reviewer to confirm this is the Maven-idiomatic pattern."

**Confirmed.** `pluginManagement` declares version and default configuration but does not bind lifecycle executions. The profile's `<build><plugins>` section activates the plugin by adding executions. Without the profile, Failsafe is inert. This is the standard Maven pattern for profile-gated lifecycle phases.
