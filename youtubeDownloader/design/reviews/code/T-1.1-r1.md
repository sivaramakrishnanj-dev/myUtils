## C3 — Minor: `PATTERN` is `public` — intentional API surface?

- **Location:** `VideoId.java:14` — `public static final Pattern PATTERN`
- **Severity:** Minor
- **Category:** API-Design
- **Spec citation:** Effective Java Item 15 (minimize accessibility)
- **Reviewer comment:**
  The design doc sample shows `PATTERN` as `public static final`. The question is whether downstream consumers (e.g., `UrlParser` in T-1.3) need to reference the compiled `Pattern` directly, or whether they only need `VideoId.of(String)` as the validation entry point. If `UrlParser` will use `PATTERN` for URL-path extraction (extracting the 11-char segment from a URL), `public` is justified. If not, package-private would reduce the public API surface per EJ Item 15.
- **Suggested fix:**
  No change required now — the design doc explicitly shows it as `public`. Flag for T-1.3 review: if `UrlParser` does not reference `VideoId.PATTERN`, consider narrowing to package-private at that point.

## C4 — Minor: Javadoc on `of(String)` could document the exception

- **Location:** `VideoId.java:22` — `public static VideoId of(String raw)`
- **Severity:** Minor
- **Category:** API-Design
- **Spec citation:** Effective Java Item 56 (write doc comments for all exposed API elements)
- **Reviewer comment:**
  The class-level Javadoc is good — it names the AC, the pattern, and the invariant. The `of` method has a one-liner comment referencing EJ Item 1, but no `@throws UrlParseException` tag. Since this is the primary construction entry point for a public API type (AC-9.1), callers benefit from seeing the exception in IDE hover.
- **Suggested fix:**
  ```java
  /**
   * Static factory — preferred construction entry point (Effective Java Item 1).
   *
   * @param raw the candidate video id string
   * @return a validated {@code VideoId}
   * @throws UrlParseException if {@code raw} is null or does not match {@link #PATTERN}
   */
  public static VideoId of(String raw) {
      return new VideoId(raw);
  }
  ```

## C6 — Discussion: INV-5 listing in the task row

- **Location:** Task row T-1.1 in `07-tasks.md`
- **Severity:** Discussion
- **Category:** Spec-Adherence
- **Spec citation:** INV-5 ("one `DownloadContext` per run — no shared mutable state between runs")
- **Reviewer comment:**
  INV-5 is about `DownloadContext` per-run isolation, not about `VideoId` validation. The implementer's argument is sound: `VideoId` being an immutable record contributes to the "no shared mutable state" guarantee (records are inherently thread-safe), and the compact constructor enforces AC-1.1 at the type boundary. However, the real INV-5 test (concurrent `download()` calls with distinct `runId` UUIDs per `contract-tests.md § 5`) belongs to a later task when `DownloadContext` exists. T-1.1 satisfies AC-1.1 directly; its relationship to INV-5 is structural (immutability) rather than behavioral. No action needed — just noting for traceability.
