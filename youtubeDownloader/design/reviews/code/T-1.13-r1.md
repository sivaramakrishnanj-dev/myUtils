## C1 — Duplicate INFO log on URL parse success

- **Location:** `Cli.java:48` (`LOGGER.info("Parsed video id: {}", ...)`) and `UrlParser.java:66` (`LOGGER.info("Parsed URL → videoId={}", ...)`)
- **Severity:** Minor
- **Category:** Readability
- **Spec citation:** AC-10.2 — "URL parsed (with videoId)" — requires the event once, not twice.
- **Reviewer comment:**
  Both `UrlParser.parse()` and `Cli.call()` emit an INFO line for the same logical event (URL parsed). The `Cli.call()` line (`"Parsed video id: {}"`) was added in T-1.12 before T-1.13 added the canonical component-boundary log in `UrlParser`. Two INFO lines for one event adds noise. Per Clean Code (SRP for log events) and AC-10.2's intent of one INFO per external-boundary event, the `UrlParser` log is the correct one — it lives at the component boundary. The `Cli.call()` line is now redundant.
- **Suggested fix:**
  Remove `LOGGER.info("Parsed video id: {}", videoId.value());` from `Cli.call()`. The `UrlParser` log already covers AC-10.2's "URL parsed (with videoId)" event.

## C2 — InnerTubeClient IOException demoted to DEBUG — correct per AC-10.4

- **Location:** `InnerTubeClient.java:117` — `LOGGER.debug(...)` in the `catch (IOException e)` block
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-10.4 — "ERROR exactly once per failure"
- **Reviewer comment:**
  Good change. The previous code logged at ERROR in `InnerTubeClient.fetchPlayer()` *and* the exception would propagate to `Cli.call()` where it would be logged at ERROR again — violating AC-10.4's "exactly once" rule. Demoting to DEBUG here means the single ERROR is emitted at the CLI boundary (`Cli.call()` catch block), which is the correct place. The DEBUG log still preserves the detail for `--debug` users.

## C4 — `configureLogging()` pre-scan approach is correct for slf4j-simple

- **Location:** `Cli.java:78–86` — `configureLogging(String[] args)` method
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-10.5 — "--debug sets effective log level to DEBUG for all loggers"
- **Reviewer comment:**
  slf4j-simple reads `org.slf4j.simpleLogger.defaultLogLevel` once at class-load time. Setting the system property *before* `CommandLine.execute()` (which triggers logger initialization) is the only way to make it work. The pre-scan approach is the right pattern for this SLF4J backend. Well-documented Javadoc explaining the "why".

## C5 — WARN test (AC-10.3) is a no-op assertion

- **Location:** `CliLoggingTest.java:82` — `WarnNotableLogs.extractor_givenUnknownStatus_logsWarn()`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** AC-10.3, Pinned Tenet 1 ("Tests are not optional")
- **Reviewer comment:**
  The test body is `assertThat(true).as("WARN path verified in yt-core unit tests").isTrue()` — a tautology. The comment explains that the real WARN test lives in `PlayerResponseExtractorNegativeTest` in yt-core, which is fair — the WARN is emitted by a yt-core component, not the CLI. However, a test method that asserts nothing is dead weight. It passes regardless of code changes and gives false confidence in the test count.
- **Suggested fix:**
  Either (a) delete this test method entirely and note in the `@Nested` class Javadoc that WARN coverage is in yt-core, or (b) replace it with a real assertion — e.g., verify that `InnerTubeRetryInterceptor`'s WARN log appears on stderr when a retry fires (which *is* a CLI-observable WARN from an M1 component). Option (a) is simpler and honest.

## C6 — `CliDebugLoggingTest` duplicates a test already in `CliLoggingTest`

- **Location:** `CliDebugLoggingTest.java:20` — `configureLogging_givenDebugFlag_setsDefaultLevelToDebug()`
- **Severity:** Minor

## C7 — Logger naming test covers all 5 M1 components
