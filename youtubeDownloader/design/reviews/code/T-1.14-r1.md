## C5 — Minor: `download(String url)` signature deviates from AC-9.1's `DownloadRequest` type

- **Location:** `YoutubeDownloader.java:52`
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** AC-9.1 — "a `DownloadRequest` input type"
- **Reviewer comment:**
  AC-9.1 specifies the library API surface as `YoutubeDownloader` + `DownloadRequest` + `DownloadResult` + exception hierarchy. The current M1 signature is `download(String url)` — no `DownloadRequest`. This is a reasonable M1 simplification since `DownloadRequest` carries flags (`audioOnly`, `maxHeight`, `transcript`, etc.) that are all M2+ concerns. However, the signature will need to change to `download(DownloadRequest)` when M2 lands, which is a breaking change for any M1 library embedder.
- **Suggested fix:**
  Acceptable for M1 — the task row says "stub `DownloadResult`" and M1 has no format selection or download flags. Flag for M2's T-2.1 or T-2.10 to introduce `DownloadRequest` and migrate the signature. No action needed now.

## C6 — Minor: Duplicate INFO log for URL parse — both UrlParser and YoutubeDownloader log it

- **Location:** `YoutubeDownloader.java:56,59` + `UrlParser.java:68`
- **Severity:** Minor
- **Category:** Observability
- **Spec citation:** AC-10.2 — "URL parsed (with videoId)" logged at INFO
- **Reviewer comment:**
  AC-10.2 requires INFO on "URL parsed (with videoId)". Both `UrlParser` (line 68: `"Parsed URL → videoId={}"`) and `YoutubeDownloader` (line 59: `"Parsed video id: {}"`) emit this at INFO. The duplicate is harmless but noisy — operators see two lines for the same event. Per *Clean Code* (Martin) — log once at the boundary that owns the event.
- **Suggested fix:**
  Consider demoting one to DEBUG. The `UrlParser` log is the natural owner (it's the component that did the work); the orchestrator's log could be DEBUG or removed. Not blocking — this is a polish item.

## C7 — Nit: `LOGGER.info("Starting download for URL: {}", url)` logs the raw URL which may contain PII-adjacent data

- **Location:** `YoutubeDownloader.java:56`
- **Severity:** Nit
- **Category:** Observability
- **Reviewer comment:**
  The raw URL is logged at INFO before parsing. YouTube URLs don't typically contain PII, but URLs with `list=` or `si=` tracking params could be considered sensitive in some contexts. AC-10.2 asks for "URL parsed (with videoId)" — the videoId is the useful datum, not the full URL. This is a taste call; the current approach is fine for a personal CLI tool.

## C8 — Discussion: AC-9.1 mentions `DownloadRequest` and `ProgressListener` — neither exists yet

- **Location:** design spec — AC-9.1 in `00-requirements.md` § Phase 1b
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** AC-9.1 — "a `DownloadRequest` input type" and "a typed exception hierarchy"
- **Reviewer comment:**
  AC-9.1 specifies four public API elements: `YoutubeDownloader`, `DownloadRequest`, `DownloadResult`, and the exception hierarchy. T-1.14 delivers `YoutubeDownloader` and `DownloadResult`; the exception hierarchy was delivered in T-1.9. `DownloadRequest` and `ProgressListener` (AC-9.3) are not yet implemented. This is expected — they carry M2+ flags. The spec doesn't gate them to a specific milestone, but the task breakdown in `07-tasks.md` implicitly defers them. No code defect here; the spec could benefit from a note that `DownloadRequest` is introduced when its fields become needed.
- **Suggested amendment kind:** ac-update (add a note to AC-9.1 that `DownloadRequest` is introduced incrementally as flags arrive)
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect.
