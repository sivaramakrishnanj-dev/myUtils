## C1 — `extractFromMobile` does not validate path — accepts any `m.youtube.com` path with `v=`

- **Location:** `UrlParser.java:60` — `case "m.youtube.com" -> extractFromMobile(raw, uri.getQuery());`
- **Severity:** Major
- **Category:** Correctness, Spec-Adherence
- **Spec citation:** AC-1.1 — "accepting at minimum: … `https://m.youtube.com/watch?v=<id>` (mobile link)." The spec enumerates `/watch?v=` as the only accepted mobile shape.
- **Reviewer comment:**
  `extractFromMobile` receives only `raw` and `query` — it never inspects the URI path. Any `m.youtube.com` URL with a `v=` query parameter is accepted regardless of path: `https://m.youtube.com/embed/foo?v=dQw4w9WgXcQ`, `https://m.youtube.com/shorts/dQw4w9WgXcQ?v=dQw4w9WgXcQ`, `https://m.youtube.com/playlist?v=dQw4w9WgXcQ` all parse successfully. AC-1.1 enumerates only `/watch?v=` for the mobile host. This is a correctness gap — the parser is more permissive than the spec allows.
  
  The `www.youtube.com` handler (`extractFromWww`) correctly validates the path is `/watch` or `/shorts/...`. The mobile handler should apply the same discipline.
- **Suggested fix:**
  Pass `path` to `extractFromMobile` and guard on `"/watch".equals(path)`:
  ```java
  private static String extractFromMobile(String raw, String path, String query) {
      if (!"/watch".equals(path)) {
          throw new UrlParseException(String.format(UNSUPPORTED_MSG, raw));
      }
      return extractVParam(raw, query);
  }
  ```
  Update the switch arm: `case "m.youtube.com" -> extractFromMobile(raw, path, uri.getQuery());`

## C2 — `youtu.be/<id>/extra` rejected by VideoId, not UrlParser — misleading error message

- **Location:** `UrlParser.java:83–87` — `extractFromShortLink`
- **Severity:** Minor
- **Category:** Readability, Spec-Adherence
- **Spec citation:** AC-1.1 short link shape is `https://youtu.be/<id>`. AC-5.1 / AC-11.4 style: error messages should name the problem.
- **Reviewer comment:**
  `extractFromShortLink` returns `path.substring(1)` without checking for extra path segments. For `https://youtu.be/dQw4w9WgXcQ/extra`, the candidate becomes `dQw4w9WgXcQ/extra` (17 chars, contains `/`), which fails `VideoId.of()` with "Invalid video id: dQw4w9WgXcQ/extra". The URL is rejected — correctness is preserved — but the error message is misleading: the problem is the URL shape, not the video id. A user seeing "Invalid video id" would not understand they need to remove the trailing path segment.

  The same issue applies to `www.youtube.com/shorts/<id>/extra` via `extractFromWww`, where `candidate` = `dQw4w9WgXcQ/extra`.
- **Suggested fix:**
  Validate that the short-link path has exactly one segment (no `/` after the id):
  ```java
  private static String extractFromShortLink(String raw, String path) {
      if (path == null || path.length() <= 1) {
          throw new UrlParseException(String.format(UNSUPPORTED_MSG, raw));
      }
      String candidate = path.substring(1);
      if (candidate.contains("/")) {
          throw new UrlParseException(String.format(UNSUPPORTED_MSG, raw));
      }
      return candidate;
  }
  ```
  Similarly for the `/shorts/` branch in `extractFromWww`, validate `candidate` contains no `/`.

## C3 — Tester: no test for `m.youtube.com` with non-watch path + `v=` param

- **Location:** `UrlParserValidationTest.java` — `InvalidUrls` section
- **Severity:** Major
- **Category:** Testing, Spec-Adherence
- **Spec citation:** AC-1.1 — mobile host accepts only `/watch?v=`. Pinned tenet 1: "Tests are not optional."
- **Reviewer comment:**
  The test `parse_givenMobileShortsUrl_throws` covers `m.youtube.com/shorts/<id>` (no `v=` param), which fails on missing `v parameter`. But there is no test for `m.youtube.com` with a non-watch path that *does* include a `v=` param — e.g., `https://m.youtube.com/embed/foo?v=dQw4w9WgXcQ` or `https://m.youtube.com/shorts/dQw4w9WgXcQ?v=dQw4w9WgXcQ`. These URLs currently pass parsing (see C1). Once C1 is fixed, a test must cover this rejection path.
- **Suggested fix:**
  Add to the `InvalidUrls` section:
  ```java
  @ParameterizedTest(name = "[{index}] {0}")
  @DisplayName("m.youtube.com — non-watch paths with v= param")
  @ValueSource(strings = {
          "https://m.youtube.com/embed/foo?v=dQw4w9WgXcQ",
          "https://m.youtube.com/shorts/dQw4w9WgXcQ?v=dQw4w9WgXcQ",
          "https://m.youtube.com/playlist?v=dQw4w9WgXcQ"
  })
  void parse_givenMobileNonWatchPathWithVParam_throws(String url) {
      assertThatThrownBy(() -> parser.parse(url))
              .isInstanceOf(UrlParseException.class);
  }
  ```

## C6 — Strict-reading decisions: `m.youtube.com/shorts` reject and `youtu.be/<id>/extra` reject

- **Location:** design spec — AC-1.1 in `00-requirements.md` § US-1
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** AC-1.1 — "accepting at minimum: `https://www.youtube.com/watch?v=<id>` … `https://youtu.be/<id>` (short link) … `https://m.youtube.com/watch?v=<id>` (mobile link)."
- **Reviewer comment:**
  The tester asks the reviewer to confirm two strict-reading decisions:
  
  1. **`m.youtube.com/shorts/<id>` → reject.** AC-1.1 enumerates `m.youtube.com/watch?v=<id>` as the mobile shape. It does not list `m.youtube.com/shorts/<id>`. The strict reading (reject) is the safer choice — accepting it would expand scope beyond the spec's enumeration. If users need it, a future AC can add it.
  
  2. **`youtu.be/<id>/extra` → reject.** AC-1.1 says `https://youtu.be/<id>` (short link). The presence of extra path segments is not part of the enumerated shape. Strict reading (reject) is correct — YouTube itself does not serve content at `youtu.be/<id>/extra`.
  
  Both decisions are defensible under the "at minimum" phrasing. The spec says "at minimum" these four shapes — it does not say "only" these shapes, but adding shapes beyond the enumeration is scope expansion, not minimum compliance. Strict is the right default for an MVP.
- **Suggested amendment kind:** Not needed at this time. If user feedback shows `m.youtube.com/shorts` is common, an `ac-update` to AC-1.1 adding a 5th shape would be appropriate.
- **Impact on this review's verdict:** none — this is a spec-interpretation confirmation, not a code defect.

## C7 — `VideoId` throws `UrlParseException` — coupling concern

- **Location:** `VideoId.java:23` — `throw new UrlParseException("Invalid video id: " + value);`
- **Severity:** Minor
- **Category:** API-Design
- **Spec citation:** Clean Code (Martin) — SRP; A Philosophy of Software Design (Ousterhout) — information hiding.
- **Reviewer comment:**
  `VideoId` is a domain value type. It throws `UrlParseException`, which semantically belongs to URL parsing. If `VideoId.of()` is later called from `PlayerResponseExtractor` (which parses `videoDetails.videoId` from InnerTube JSON), a `UrlParseException` would be misleading — the input wasn't a URL. T-1.9 will introduce the full exception hierarchy; this coupling will likely be resolved then. Noting it here so it's not forgotten.
- **Suggested fix:**
  No action needed now — T-1.9 (exception hierarchy) is the right place to address this. The implementer's stub comment in `UrlParseException.java` already notes "T-1.9 will rehome it."
