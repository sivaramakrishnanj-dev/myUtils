## Round 1 finding resolution

### C1 — `extractFromMobile` does not validate path — **RESOLVED** ✅

The implementer added `path` as a parameter to `extractFromMobile` and guards with `if (!"/watch".equals(path))` before extracting the `v=` parameter. The switch arm now passes `path` through: `case "m.youtube.com" -> extractFromMobile(raw, path, uri.getQuery())`.

Verified by tracing: `https://m.youtube.com/embed/foo?v=dQw4w9WgXcQ` → host matches `m.youtube.com` → `extractFromMobile(raw, "/embed/foo", "v=dQw4w9WgXcQ")` → `"/watch".equals("/embed/foo")` is false → throws `UrlParseException` with "Unsupported URL" message. Correct.

### C2 — `youtu.be/<id>/extra` rejected by VideoId, not UrlParser — **RESOLVED** ✅

The implementer added `candidate.contains("/")` checks in both `extractFromShortLink` (line 90) and the `/shorts/` branch of `extractFromWww` (line 72). Both now throw `UrlParseException` with the `UNSUPPORTED_MSG` format — the error message correctly says "Unsupported URL", not "Invalid video id".

Verified: `https://youtu.be/dQw4w9WgXcQ/extra` → `extractFromShortLink` → `candidate = "dQw4w9WgXcQ/extra"` → `candidate.contains("/")` is true → throws with "Unsupported URL". Same for `https://www.youtube.com/shorts/dQw4w9WgXcQ/extra`.

### C3 — No test for `m.youtube.com` with non-watch path + `v=` param — **RESOLVED** ✅

The tester added a parameterized test `parse_givenMobileNonWatchPathWithVParam_throws` with 5 cases:
1. `https://m.youtube.com/embed/foo?v=dQw4w9WgXcQ`
2. `https://m.youtube.com/shorts/dQw4w9WgXcQ?v=dQw4w9WgXcQ`
3. `https://m.youtube.com/playlist?v=dQw4w9WgXcQ`
4. `https://m.youtube.com/channel/UC1234?v=dQw4w9WgXcQ`
5. `https://m.youtube.com/?v=dQw4w9WgXcQ`

All assert `UrlParseException` with `hasMessageContaining("Unsupported URL")` — verifying both the rejection and the error message quality. These tests would have caught the original C1 bug (all 5 would have passed before the fix, since the old code accepted any `m.youtube.com` path with `v=`). Test count: 43 (was 38). Meaningful coverage of the new reject branch.

### C7 — `VideoId` throws `UrlParseException` coupling — **ACCEPTED (deferred to T-1.9)** ✅

Round 1 explicitly noted "No action needed now — T-1.9 (exception hierarchy) is the right place." No change expected or needed this round.

### C6 — Strict-reading decisions (Discussion) — **UNCHANGED** ✅

Still appropriate. The strict reading of AC-1.1 (reject `m.youtube.com/shorts/<id>` and `youtu.be/<id>/extra`) is now enforced in code and tested. No spec amendment needed at this time.
