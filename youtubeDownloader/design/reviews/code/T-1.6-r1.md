## C1 — Clean interceptor design with injectable Sleeper

- **Location:** `InnerTubeRetryInterceptor.java` (entire class)
- **Severity:** Praise
- **Category:** API-Design
- **Spec citation:** AC-12.4, ADR-0002
- **Reviewer comment:**
  The interceptor is well-factored: single responsibility, package-private visibility (correct for an internal utility), injectable `Sleeper` for testability with no static time coupling. The loop structure is clear — `attempt 0..MAX_RETRIES` with early return on success or non-retryable status, and final-attempt pass-through that returns the response as-is (retryable status) or rethrows (IOException). This matches the ADR-0002 consequence: "Retry interceptor is single-file." Clean Code SRP.

- **Location:** `InnerTubeRetryInterceptor.java:73` — `response.close()`

## C4 — Consider logging the retryable HTTP status code in the WARN message

- **Location:** `InnerTubeRetryInterceptor.java:63`
- **Severity:** Minor
- **Category:** Observability
- **Spec citation:** AC-10.2, AC-10.3, SHARED.md § 3
- **Reviewer comment:**
  The WARN log on retry (`"InnerTube retry {}/{} after {}ms"`) includes the retry count and delay but not the trigger — whether it was an IOException or which HTTP status code caused the retry. For a maintainer diagnosing why retries are happening (US-10, P4), knowing "retry 1/3 after 500ms (HTTP 503)" vs "retry 1/3 after 500ms (IOException: Connection reset)" is valuable. SHARED.md § 3 says WARN on non-fatal notables; the trigger is the notable part.
- **Suggested fix:**
  Add the trigger to the log message. For the HTTP-status path, log the status code before closing the response. For the IOException path, log the exception message. Example: `LOGGER.warn("InnerTube retry {}/{} after {}ms — triggered by HTTP {}", attempt, MAX_RETRIES, delayMs, response.code())` and `LOGGER.warn("InnerTube retry {}/{} after {}ms — triggered by {}", attempt, MAX_RETRIES, delayMs, e.getMessage())`.

## C5 — `create()` integration tests use reflection — acceptable but fragile

- **Location:** `InnerTubeRetryInterceptorBehaviorTest.java:268–300` (CreateIntegration nested class)
- **Severity:** Nit
- **Category:** Testing
- **Reviewer comment:**
  The two `create()` integration tests use reflection to access `InnerTubeClient.httpClient` and `InnerTubeRetryInterceptor.sleeper` private fields. This is fragile against field renames but acceptable here because: (a) the fields are in the same package and under the same team's control, (b) OkHttp's `OkHttpClient.interceptors()` is public so the first test could avoid reflection for the interceptor list check, and (c) the `InnerTubeClientFactoryTest` already covers timeout configuration via the same reflection pattern — establishing a project convention. The slight overlap between `InnerTubeClientFactoryTest.InterceptorWiring` and `CreateIntegration` is noted by the tester and is acceptable — they test different things (factory config vs retry behavior wiring).
- **Suggested fix:**
  For the first test, `OkHttpClient.interceptors()` is public — the reflection on `InnerTubeClient.httpClient` could be replaced by exposing a package-private accessor or using the existing `extractHttpClient` helper from `InnerTubeClientFactoryTest`. Not blocking.
