## C1 — Null input throws `IllegalArgumentException`, not `InnerTubeParseException`

- **Location:** `PlayerResponseExtractor.java:52` — `extract(String json)` method
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** ADR-0004 ("Typed errors on required-field failure … rethrows as `InnerTubeParseException`")
- **Reviewer comment:**
  When `json` is `null`, Jackson's `readTree(null)` throws `IllegalArgumentException`, which is not caught by the `catch (JsonProcessingException e)` block. The exception propagates unwrapped. ADR-0004 says all parse failures surface as `InnerTubeParseException`. A null input is a degenerate parse failure — the caller should see the same typed exception as for malformed JSON. The tester correctly flagged this inconsistency and wrote a loose assertion (`isInstanceOfAny`) to document the current behavior.
- **Suggested fix:**
  Add a null guard at the top of `extract()`:
  ```java
  if (json == null) {
      throw new InnerTubeParseException("InnerTube JSON input is null");
  }
  ```
  Then tighten the tester's assertion in `extract_givenNullInput_throwsException` to `isInstanceOf(InnerTubeParseException.class)`.

## C2 — Tester's null-input assertion is too loose

- **Location:** `PlayerResponseExtractorNegativeTest.java:233` — `extract_givenNullInput_throwsException`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** Pinned tenet 1 ("Tests are not optional") + ADR-0004 typed-exception contract
- **Reviewer comment:**
  The test uses `isInstanceOfAny(InnerTubeParseException.class, NullPointerException.class, IllegalArgumentException.class)` — three possible types. This documents the current ambiguity rather than asserting the contract. Once C1 is fixed, this should assert exactly `InnerTubeParseException.class`. As-is, it would silently pass if a future refactor changed the exception type to any of the three, defeating the contract-test purpose.
- **Suggested fix:**
  After C1 is applied, change to:
  ```java
  assertThatThrownBy(() -> PlayerResponseExtractor.extract(null))
          .isInstanceOf(InnerTubeParseException.class);
  ```

## C3 — `parseFormat` does not guard against null `itag`/`mimeType`/`bitrate` nodes

- **Location:** `PlayerResponseExtractor.java:109–112` — `parseFormat(JsonNode f)`
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** ADR-0004 ("Typed errors on required-field failure"), *Release It!* (defensive parsing at trust boundaries)
- **Reviewer comment:**
  `f.get("itag").asInt()`, `f.get("mimeType").asText()`, and `f.get("bitrate").asLong()` will throw `NullPointerException` if any of those fields is absent from a format entry. The extractor correctly uses `requireNode`/`requireString` for top-level required fields but not for per-format required fields. A malformed format entry in the InnerTube response would produce an NPE instead of `InnerTubeParseException`. This is a minor reliability gap — InnerTube responses in practice always have these fields, but the defensive pattern is already established elsewhere in the class.
- **Suggested fix:**
  Use `requireString(f, "mimeType")` and similar guards, or wrap the per-format parse in a try-catch that converts NPE to `InnerTubeParseException` with the format's index for debuggability.

## C4 — Unknown `PlayabilityStatus` → `UNKNOWN` is correct per spec

- **Location:** `PlayerResponseExtractor.java:96–100` — `parsePlayabilityStatus`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** `03-data-model.md` § 2.7 — `UNKNOWN` sentinel; AC-5.2 exit 11 not 20
- **Reviewer comment:**
  The implementer correctly maps unrecognized status strings to `PlayabilityStatus.UNKNOWN` with a WARN log, rather than throwing. This is the right call: the extractor's job is to parse, not to enforce playability policy. T-1.8 (post-parse playability check) will decide whether `UNKNOWN` is fatal. The WARN log gives the maintainer (P4) a signal without crashing the run. Clean separation of concerns.

## C5 — Graceful degradation for `audioSampleRate` and `contentLength`

- **Location:** `PlayerResponseExtractor.java:155–180` — `optionalIntFromString`, `optionalLongFromString`
- **Severity:** Praise
- **Category:** Reliability
- **Spec citation:** ADR-0004 ("graceful wire-type conversion"), AC-11.1 (pure function)
- **Reviewer comment:**
  InnerTube sends `audioSampleRate` as a string (`"44100"`) and occasionally as a number. The extractor handles both via `node.asText()` + `Integer.parseInt`, degrading to `OptionalInt.empty()` with a WARN on unparseable values. Same pattern for `contentLength`. This is exactly the ADR-0004 "permissive-by-default" discipline — the tool doesn't crash on wire-type drift, and the WARN gives the maintainer a signal. Well done.

## C10 — AC-2.3 retry budget is not pinned as an NFR for the extractor

- **Location:** design spec — AC-11.1 in `00-requirements.md` § 2
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** AC-11.1, ADR-0004
- **Reviewer comment:**
  AC-11.1 requires the InnerTube response parser to be a "pure function over in-memory inputs, with no network or filesystem I/O embedded." The extractor satisfies this — it takes a `String`, returns a `PlayerResponse`, and does no I/O. However, the spec is silent on whether the extractor should validate the *semantic* consistency of the response (e.g., `url.isEmpty() == hasCipher()` invariant from `03-data-model.md` § 2.7). Currently the extractor does not enforce this — it faithfully parses whatever InnerTube sends. This is probably correct (validation belongs in `FormatSelector` per the component split), but the spec could be clearer about where semantic validation lives.
- **Suggested amendment kind:** ac-update (clarify that AC-11.1 covers syntactic parsing only; semantic validation is downstream)
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect.
