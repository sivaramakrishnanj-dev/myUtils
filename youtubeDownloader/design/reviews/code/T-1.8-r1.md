## C1 — UNKNOWN exception message omits videoId

- **Location:** `PlayerResponseExtractor.java:84–85` — `checkPlayability()`, UNKNOWN branch
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** AC-5.1 ("the message identifies which boundary failed"), cli-exit-codes.md § 1 exit 11 template `"Error: innertube: response shape unexpected — {field}"`
- **Reviewer comment:**
  The `LiveStreamException` and `VideoUnavailableException` messages both include `details.videoId().value()`, which is good for operator diagnosis (AC-5.1). The `InnerTubeParseException` for UNKNOWN does not — it says `"Unknown playabilityStatus — response shape may have changed"` with no videoId and no indication of what the actual unrecognized status string was. Including the videoId and the raw status value would make debugging easier when YouTube introduces a new status.
- **Suggested fix:**
  ```java
  throw new InnerTubeParseException(
          "Unknown playabilityStatus — response shape may have changed: " + details.videoId().value());
  ```
  Or even better, include the raw status: but since `checkPlayability` receives a parsed `PlayerResponse` where the status is already `UNKNOWN` (the raw string was lost in `parsePlayabilityStatus`), the videoId alone is the actionable addition here.

## C2 — CT-APP-7 message assertion not verified

- **Location:** `CheckPlayabilityTest.java:117` — `checkPlayability_givenUnplayableFixture_throwsVideoUnavailableException`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** CT-APP-7 in contract-tests.md: "Post-parse throws `VideoUnavailableException` with message 'This video is private.'"
- **Reviewer comment:**
  CT-APP-7 specifies the exception message should contain the InnerTube reason string `"This video is private."`. The test only asserts `isInstanceOf(VideoUnavailableException.class)` — it does not verify the message content. The implementation's message is `"Video unavailable (UNPLAYABLE): privprivpr1"`, which does not include the InnerTube `reason` field at all. This is a partial CT-APP-7 satisfaction — the exception type is correct, but the message content diverges from the contract test's assertion column. Since the implementation doesn't have access to the `reason` field (it's not modelled in `PlayabilityStatus` or `PlayerResponse`), this is more of a spec/design gap than a code bug — the `reason` string from InnerTube's `playabilityStatus.reason` is not parsed by `PlayerResponseExtractor.extract()`. Flagging as Minor because the exit code mapping (the primary concern of AC-5.2) is correct; the message content is a quality-of-life issue for the CLI user.
- **Suggested fix:**
  For now, the test should at minimum assert the message contains the videoId (matching the implementation's actual output). The `reason` field gap is a design-level concern — see Discussion C7 below.

## C7 — InnerTube `reason` field not propagated to exception message

- **Location:** design spec — CT-APP-7 in `contract-tests.md`, cli-exit-codes.md § 1 exit 20 template
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** CT-APP-7, cli-exit-codes.md § 1 exit 20 message template `"Error: unavailable: {reason_from_innertube}"`
- **Reviewer comment:**
  CT-APP-7 asserts the exception message should be `"This video is private."` — the InnerTube `reason` field. The exit-20 message template in cli-exit-codes.md § 1 says `"Error: unavailable: <reason from InnerTube>"`. However, `PlayerResponseExtractor.extract()` does not parse the `playabilityStatus.reason` string from the InnerTube response — it only parses `playabilityStatus.status` (the enum). The `PlayerResponse` record has no field for the reason string. This means the implementation cannot satisfy the message template as written. The current message `"Video unavailable (UNPLAYABLE): <videoId>"` is functional but diverges from the spec's intent of surfacing YouTube's own reason text.
- **Suggested amendment kind:** `schema-update` — add `Optional<String> playabilityReason` to `PlayerResponse` (or `VideoDetails`), parse it from `playabilityStatus.reason` in `extract()`, and thread it into the `VideoUnavailableException` message. This would also require updating `data-model.md` § 2.7 and `innertube-player-response.schema.json`.
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect. The exit-code mapping (the primary concern of AC-5.2) is correct.
