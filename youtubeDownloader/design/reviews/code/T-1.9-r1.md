## C4 — Constructor split is well-reasoned

- **Location:** all 11 subclasses
- **Severity:** Praise
- **Category:** API-Design
- **Reviewer comment:**
  Domain-decision exceptions (video unavailable, live stream, cipher required, no matching format, caption unavailable, output exists) expose only `(String)` — they represent application-level decisions with no underlying cause to chain. Wrapping exceptions (NetworkException, InnerTubeParseException, FfmpegException, FilesystemException) expose both `(String)` and `(String, Throwable)` — they wrap I/O or external-process failures where the cause chain is diagnostic gold. `UrlParseException` is message-only, which is correct — it's a validation failure, not a wrapping exception. Clean API design per Effective Java item 72 (favor standard exceptions) and item 73 (throw exceptions appropriate to the abstraction).

## C5 — `InnerTubeClient.buildRequestBody` wraps `JsonProcessingException` as `NetworkException`

- **Location:** `InnerTubeClient.java:149`
- **Severity:** Minor
- **Category:** Correctness
- **Spec citation:** `cli-exit-codes.md` § 3 — code 10 is "network" category
- **Reviewer comment:**
  `buildRequestBody` catches `JsonProcessingException` and wraps it in `NetworkException("Failed to serialize InnerTube request body", e)`. A JSON serialization failure on a hand-built `ObjectNode` is a programming error, not a network error. The comment says "Should never happen" — and it shouldn't — but if it did, exit code 10 ("network") would be misleading. An `IllegalStateException` or an `InnerTubeParseException` (exit 11, "innertube") would be more accurate. This is pre-existing code from T-1.5, not introduced by T-1.9, so it's not a blocker for this task. Flagging for awareness.
- **Suggested fix:**
  Consider `throw new IllegalStateException("Failed to serialize InnerTube request body", e)` since this is a "should never happen" branch, or wrap in `InnerTubeParseException` if you want it to stay in the hierarchy.

## C9 — Spec says "checked", implementation is unchecked (`RuntimeException`)

- **Location:** `YoutubeDownloaderException.java:15` — `extends RuntimeException`
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** AC-9.1 ("a typed exception hierarchy rooted at a single checked `YoutubeDownloaderException`"), `04-apis.md` § 3.2.2 ("All exceptions are **checked**."), `02-architecture.md` § 6 (`// checked base`)
- **Reviewer comment:**
  AC-9.1 specifies "a typed exception hierarchy rooted at a single checked `YoutubeDownloaderException`". `04-apis.md` § 3.2.2 states "All exceptions are **checked**. The library's contract is that `download()` either returns a `DownloadResult` or throws a specific subtype of `YoutubeDownloaderException`. No `RuntimeException` subtypes are thrown from normal failure paths." `02-architecture.md` annotates the base as `// checked base`.

  The implementation extends `RuntimeException` (unchecked). The Javadoc explains: "Unchecked (extends RuntimeException) — callers catch at the top-level orchestration boundary, not at every intermediate call site."

  This is a defensible design choice — unchecked exceptions avoid polluting every intermediate method signature with `throws YoutubeDownloaderException`, and the sealed hierarchy still gives callers compile-time exhaustiveness guarantees. But it contradicts the spec in three places. The T-1.5 review (C3) and T-1.1 review both explicitly expected T-1.9 to make the hierarchy checked.

  This is a spec-level observation, not a code defect. The code is internally consistent and well-designed. The spec should be updated to match the implementation's choice, or the implementation should be changed to match the spec.
- **Suggested amendment kind:** `ac-update` (update AC-9.1 to say "unchecked" instead of "checked"; update `04-apis.md` § 3.2.2 to remove the "checked" assertion; update `02-architecture.md` § 6 comment)
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect.
