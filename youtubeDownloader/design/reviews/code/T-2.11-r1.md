## C1 — AC-1.3 default `--max-height` is 0 (uncapped), spec says 1080

- **Location:** `Cli.java:49` — `@Option(names = "--max-height", ... defaultValue = "0")`
- **Severity:** Blocker
- **Category:** Spec-Adherence
- **Spec citation:** AC-1.3: "The system SHALL filter the available video formats to those whose `height ≤ max-height` (**default 1080**, user-overridable via `--max-height`; `--max-height 0` disables the cap)."
- **Reviewer comment:**
  AC-1.3 explicitly pins the default to 1080. The implementation sets `defaultValue = "0"`, which means uncapped by default. This inverts the spec's intent: users who omit `--max-height` would get the highest resolution available (potentially 4K/8K), whereas the spec intends a 1080p cap unless the user explicitly opts out with `--max-height 0`. The coordinator's briefing note ("default 0 per AC-1.3") misread the AC.
- **Suggested fix:**
  Change `defaultValue = "0"` to `defaultValue = "1080"` in `Cli.java`. Update the `@Option` description to match: `"Maximum video height; 0 = uncapped (default: 1080)"`.

## C2 — Convenience overload `download(String, ProgressListener)` passes `maxHeight = 0`

- **Location:** `YoutubeDownloader.java:95` — `new DownloadRequest(url, false, 0, ...)`
- **Severity:** Blocker
- **Category:** Spec-Adherence
- **Spec citation:** AC-1.3 (same as C1)
- **Reviewer comment:**
  The library convenience overload that wraps a raw URL into a `DownloadRequest` hard-codes `maxHeight = 0` (uncapped). Per AC-1.3, the default should be 1080. Library embedders (P3) calling `download(url, listener)` would get uncapped resolution, contradicting the spec. The same applies to the single-arg `download(String url)` which delegates to this overload.
- **Suggested fix:**
  Change `0` to `1080` in the convenience overload. Consider extracting a constant `public static final int DEFAULT_MAX_HEIGHT = 1080` on `DownloadRequest` so the default is defined once and referenced by both `Cli` and `YoutubeDownloader`.

## C3 — `CliMaxHeightBehaviorTest` test 3 asserts wrong default semantics

- **Location:** `CliMaxHeightBehaviorTest.java:56` — `execute_givenNoMaxHeight_exitsZeroWithDefault()`
- **Severity:** Blocker
- **Category:** Testing
- **Spec citation:** AC-1.3
- **Reviewer comment:**
  Test 3 is titled "AC-1.3: no --max-height → default 0 (uncapped), exit 0" and asserts only that exit code is 0. The test's title and intent encode the wrong default (0 instead of 1080). After C1 is fixed (default becomes 1080), this test's title should be updated to reflect the correct default. The assertion itself (exit 0) remains valid, but the test should ideally verify that the `maxHeight` field on the constructed `DownloadRequest` is 1080 when no flag is given — otherwise it's not actually testing the default-value semantics of AC-1.3.
- **Suggested fix:**
  Rename to "AC-1.3: no --max-height → default 1080, exit 0". Consider adding an assertion that captures the `DownloadRequest` passed to the downloader and verifies `maxHeight == 1080` (e.g., via a capturing fake).

## C4 — `DownloadRequest.audioOnly(...)` factory hard-codes `maxHeight = 0`

- **Location:** `DownloadRequest.java:24` — `return new DownloadRequest(url, true, 0, output, ProgressListener.NO_OP);`
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** AC-1.3, AC-2.5
- **Reviewer comment:**
  The `audioOnly` factory passes `maxHeight = 0`. For audio-only mode, `maxHeight` is semantically irrelevant (audio selection ignores it), so this is not a correctness bug. However, for consistency with the spec default and to avoid confusion when AC-2.5 is implemented (warning when `--audio-only` + `--max-height` are combined), using the spec default (1080) or the extracted constant would be cleaner. Not blocking — the audio path ignores this field.
- **Suggested fix:**
  Use `DEFAULT_MAX_HEIGHT` (once extracted per C2) or leave as 0 with a comment: `// maxHeight irrelevant for audio-only; 0 is fine`.

## C5 — Negative `--max-height` accepted without validation

- **Location:** `Cli.java:49` — `private int maxHeight`; `CliMaxHeightBehaviorTest.java:82` — test 5
- **Severity:** Minor
- **Category:** Correctness
- **Spec citation:** AC-1.3
- **Reviewer comment:**
  AC-1.3 defines `maxHeight` as a height cap: "height ≤ max-height". A negative value (e.g., `--max-height -1`) would filter out all video formats (no format has height ≤ -1), producing a `NoMatchingFormatException` at format-selection time. This is arguably correct behaviour (fail fast), but the error message would be "no video format matches the selection criteria (max-height=-1)" rather than a clear "invalid argument" message. The tester's test 5 documents this as "picocli accepts negative int, exit 0" — but exit 0 only holds because the current non-audio-only path returns a metadata stub without calling `FormatSelector.select()`. Once M3 wires the video path, `--max-height -1` will exit 30, not 0.
- **Suggested fix:**
  Add a picocli `@Option` validator or a guard in `Cli.call()` that rejects negative values with exit 2 and a message like `Error: args: --max-height must be 0 (uncapped) or a positive integer`. Update test 5 to expect exit 2 for negative values.
