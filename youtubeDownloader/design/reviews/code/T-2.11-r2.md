## New findings on round-2 diff

## C1 — Defense-in-depth: compact ctor + CLI guard is clean layering

- **Location:** `DownloadRequest.java:30–33` (compact ctor) + `Cli.java:69–71` (early guard)
- **Severity:** Praise
- **Category:** Correctness
- **Spec citation:** AC-1.3
- **Reviewer comment:**
  Two-layer validation is the right pattern: the CLI throws `UrlParseException` (exit 2, user-facing message), while the record's compact constructor throws `IllegalArgumentException` as a belt-and-braces guard for library embedders (P3). Neither layer is redundant — they serve different callers with different error contracts.

## C2 — `DEFAULT_MAX_HEIGHT` constant is the single source of truth

- **Location:** `DownloadRequest.java:27`
- **Severity:** Praise
- **Category:** Reuse
- **Spec citation:** AC-1.3
- **Reviewer comment:**
  Extracting `DEFAULT_MAX_HEIGHT = 1080` on `DownloadRequest` and referencing it from `YoutubeDownloader.download(String, ProgressListener)` and `Cli.java`'s `defaultValue = "1080"` ensures the spec default is defined once. The `defaultValue` string in the `@Option` annotation cannot reference a constant (picocli limitation), but the numeric value matches. Good.

## C3 — `DownloadRequest.audioOnly()` still passes `maxHeight = 0` (carried from r1-C4)

- **Location:** `DownloadRequest.java:36`
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** AC-1.3, AC-2.5
- **Reviewer comment:**
  Carried from round 1 (C4). The `audioOnly()` factory passes `maxHeight = 0` (uncapped). For audio-only mode, `maxHeight` is semantically irrelevant — `FormatSelector.selectAudioOnly()` ignores it. Not a correctness bug. A comment would clarify intent for future readers.
- **Suggested fix:**
  Add inline comment: `// maxHeight irrelevant for audio-only; 0 is acceptable`.

## C4 — Test 3 does not assert `maxHeight == 1080` on the constructed request

- **Location:** `CliMaxHeightBehaviorTest.java:72–78`
- **Severity:** Nit
- **Category:** Testing
- **Spec citation:** AC-1.3
- **Reviewer comment:**
  Test 3 verifies exit 0 when no `--max-height` is given, which confirms the default is valid. It does not capture the `DownloadRequest` to assert `maxHeight == 1080`. The `FakeDownloaderFactory` doesn't expose a capturing hook. This is a minor gap — the default is already pinned by the `@Option(defaultValue = "1080")` annotation, and a picocli annotation test would be brittle. Acceptable as-is.
