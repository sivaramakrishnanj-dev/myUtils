## C1 — `isRetryable` relies on string-matching exception messages

- **Location:** `StreamDownloader.java:225` — `isRetryable(NetworkException)`
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** AC-12.4 (retryable-error whitelist)
- **Reviewer comment:**
  `isRetryable` determines retry eligibility by scanning `e.getMessage()` for substrings like `"HTTP 500"`. The message is constructed in `doDownload` at line 193 with `"CDN GET " + hostOf(url) + " returned HTTP " + code`, so the coupling works today. However, the contract between the two methods is implicit — a future refactor of the error message (e.g., `"status 500"` or localized text) would silently break retry logic. *A Philosophy of Software Design* (Ousterhout) — information leakage between methods via implicit format contracts.
  The `InnerTubeRetryInterceptor` avoids this entirely by checking `response.code()` directly against `RETRYABLE_STATUSES` before constructing any exception. Here, the retry loop wraps `doDownload` which already throws `NetworkException`, so the status code is lost by the time `isRetryable` runs.
- **Suggested fix:**
  Carry the HTTP status code in `NetworkException` (e.g., an `Optional<Integer> httpStatus()` accessor, or a package-private subclass `HttpNetworkException`). Then `isRetryable` checks `e.httpStatus().map(RETRYABLE_STATUSES::contains).orElse(e.getCause() instanceof IOException)`. This is a Minor because the current code is correct and tested — the fragility is latent, not active.

## C2 — `truncateToSize` swallows IOException on truncation failure

- **Location:** `StreamDownloader.java:253` — `truncateToSize` catch block
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** INV-15 (progress monotonicity / cross-invocation resume preservation)
- **Reviewer comment:**
  If `FileChannel.truncate()` or `Files.delete()` throws, the method logs a WARN and returns silently. The retry then proceeds with a file that may contain stale partial bytes from the failed attempt, potentially producing a corrupt download that passes no further validation. *Release It!* (Nygard) — silent fallbacks on data-integrity errors are a COE anti-pattern.
  In practice, truncation failure on a local filesystem is rare (permissions, disk error), and the download would likely fail again on the next write attempt anyway. But the failure mode is silent corruption rather than a clear error.
- **Suggested fix:**
  Rethrow as `NetworkException` so the retry loop treats truncation failure as non-retryable and surfaces the real problem. Alternatively, if the preference is to keep the current lenient behavior, add a comment explaining why silent fallback is acceptable here.

## C7 — AC-12.4 retryable whitelist applied to stream downloads

- **Location:** design spec — AC-12.4 in `00-requirements.md` § 12
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** AC-12.4, `02-architecture.md` § 4.2
- **Reviewer comment:**
  AC-12.4 is scoped to InnerTube requests: "IF an **InnerTube request** fails with an HTTP 5xx OR a network error, THEN the system SHALL retry..." The task row for T-2.4 references AC-12.4 for stream retries, and the implementation applies the same retryable whitelist (429 + 5xx + IOException). Architecture § 4.2 says only "Retryable: connection reset, read timeout" for streams — it does not mention HTTP status codes.
  The implementation's choice to include HTTP 429/5xx in the stream retry whitelist is reasonable and defensive (CDN rate-limiting and transient server errors are real). But the spec doesn't explicitly mandate it for streams — AC-12.4 is InnerTube-specific, and § 4.2 only names IOException-type failures.
- **Suggested amendment kind:** ac-update (add an AC-12.5 or extend AC-12.4 to cover stream download retries with their own retryable-status whitelist, or update § 4.2 to name the HTTP codes explicitly)
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect. The implementation is correct and well-tested.
