## C1 — `formatEta` uses `m:ss` but operations doc example shows `MM:SS`

- **Location:** `ProgressReporter.java:131` — `formatEta` method
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** `05-operations.md` § 2.2 example progress line: `[video]    45%   112.3 MB / 249.1 MB   9.8 MB/s   ETA 00:14`
- **Reviewer comment:**
  The operations doc example shows `ETA 00:14` (zero-padded two-digit minutes). The implementation produces `ETA 0:14` (no zero-padding). AC-4.1 says "estimated time remaining" without pinning a format, so the operations doc example is illustrative, not normative. However, the zero-padded format is more consistent with the `HH:MM:SS,mmm` convention used elsewhere in the project (AC-6.2 SRT timestamps). Additionally, for values ≥ 3600s the code produces `60:00` rather than `1:00:00` — this is functional but may confuse users expecting an hours component. The tester flagged this; the spec is silent on the exact ETA format.
- **Suggested fix:**
  Consider `String.format("ETA %d:%02d:%02d", h, m, s)` for ≥ 3600s and `String.format("ETA %02d:%02d", m, s)` for < 3600s. Or keep `m:ss` and document the choice in a `rationale_for_significant_choices` note. Either is acceptable — this is a Minor, not a blocker.

## C2 — `ProgressReporterTest` uses `Thread.sleep(1200)` — timing-dependent

- **Location:** `ProgressReporterTest.java:33–38`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** AC-11 (offline-testable), NFR-UNIT-TEST-RUNTIME-BUDGET = 30s
- **Reviewer comment:**
  The characterization test sleeps 1200ms waiting for the real scheduler to fire. This is timing-dependent and contributes 1.2s to the test budget (4% of the 30s NFR). The `ProgressReporterBehaviorTest` already covers the same ground deterministically via the `StubScheduler`. The characterization test adds marginal value over the behavior test and introduces flakiness risk on slow CI runners (*Clean Code* — tests should be fast and deterministic).
- **Suggested fix:**
  Either reduce the sleep to the minimum needed (e.g., 200ms with a shorter scheduler interval injected), or mark this test as a characterization test that can be excluded from the fast suite if it becomes flaky. Not blocking — the behavior test is the real coverage.

## C3 — `close()` does not `awaitTermination` before final render

- **Location:** `ProgressReporter.java:93–103` — `close()` method
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** `02-architecture.md` § 6 — "the only background thread in the process"
- **Reviewer comment:**
  After `renderTask.cancel(false)` and `scheduler.shutdown()`, the code immediately calls `render()` for the final output. If a scheduled render is mid-execution at that moment, both renders run concurrently on the same `PrintWriter`. `PrintWriter` synchronizes internally so no corruption occurs, but the output could show a partial scheduled line interleaved with the final line. In practice this is unlikely (the render is fast), but adding `scheduler.awaitTermination(100, MILLISECONDS)` between `shutdown()` and the final `render()` would close the window cleanly (*Release It!* — clean shutdown ordering).
- **Suggested fix:**
  ```java
  scheduler.shutdown();
  try { scheduler.awaitTermination(100, TimeUnit.MILLISECONDS); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
  // then final render
  ```

## C4 — `startNanos` race window is correctly guarded by volatile ordering

- **Location:** `ProgressReporter.java:47–48` — `startNanos` and `started` fields
- **Severity:** Praise
- **Category:** Correctness
- **Reviewer comment:**
  The `volatile` on both `startNanos` and `started`, combined with the write order in `onProgress` (write `startNanos` before `started`) and the read order in `render` (read `started` before `startNanos`), establishes a correct happens-before chain. ## C7 — ETA format for large values (≥ 3600s) — spec is silent

- **Location:** design spec — AC-4.1 in `00-requirements.md` § US-4
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** AC-4.1, `05-operations.md` § 2.2
- **Reviewer comment:**
  AC-4.1 requires "estimated time remaining" but does not pin a format. The operations doc example shows `ETA 00:14` (implying `MM:SS`), but no spec covers what happens when ETA exceeds 59:59. The implementation uses `m:ss` throughout, producing `60:00` for 3600s. This is functional but could confuse users who expect `1:00:00`. The spec should pin the ETA format — either `m:ss` (unbounded minutes), `MM:SS` (zero-padded, unbounded), or `H:MM:SS` (with hours when ≥ 3600s). This is a spec gap, not a code defect.
- **Suggested amendment kind:** `ac-update` (pin ETA display format in AC-4.1 or add a new NFR-PROGRESS-ETA-FORMAT)
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect.
