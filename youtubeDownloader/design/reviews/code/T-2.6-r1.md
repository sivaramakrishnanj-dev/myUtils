- **Severity:** Praise
- **Category:** API-Design

## C3 — `StderrProgressListener` correctly placed in `yt-cli`

- **Location:** `yt-cli/src/main/java/com/srk/myutils/yd/cli/StderrProgressListener.java`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-9.3, `02-architecture.md` § 1.2.4
- **Reviewer comment:**
  AC-9.3 requires the library to not write to `System.out` or `System.err` directly — all output through an injectable listener. Placing `StderrProgressListener` in `yt-cli` (not `yt-core`) respects this boundary. The architecture doc says "CLI provides a stderr-writing listener; library embedders supply their own" — this is exactly that. The delegation to `ProgressReporter.forStderr()` keeps the rendering logic in `yt-core` (where it belongs, since `ProgressReporter` is a core component) while the CLI-specific wiring stays in `yt-cli`.

## C4 — `StderrProgressListener` constructor always creates a new `ProgressReporter` — no reuse or injection

- **Location:** `StderrProgressListener.java:13`
- **Severity:** Minor
- **Category:** API-Design
- **Spec citation:** AC-9.3
- **Reviewer comment:**
  The constructor hard-codes `ProgressReporter.forStderr()`. This is fine for the CLI's single-use pattern (one listener per run), but it means the class is not testable without capturing `System.err` and using `Thread.sleep` — which is exactly what `StderrProgressListenerBehaviorTest` does. A package-private constructor accepting a `ProgressReporter` would make the tests deterministic and faster. Not a blocker — the current tests work and the class is thin — but worth noting for future maintainability (*Clean Code* — dependency injection for testability).
- **Suggested fix:**
  Add a package-private constructor `StderrProgressListener(ProgressReporter delegate)` for testing. The public no-arg constructor remains the production entry point.

## C5 — `StderrProgressListenerBehaviorTest` uses `Thread.sleep` for timing

- **Location:** `StderrProgressListenerBehaviorTest.java:27` (`Thread.sleep(1200)`) and `:46` (`Thread.sleep(500)`)
- **Severity:** Minor
- **Category:** Testing
- **Reviewer comment:**
  `Thread.sleep(1200)` to wait for the scheduled executor to render is a flaky-test smell — on a loaded CI machine, the scheduler might not fire within 1200ms. The test passes today because the non-TTY interval is 1000ms and 1200ms gives 200ms headroom, but this is fragile. Relates to C4 — with an injectable `ProgressReporter` (or an injectable `ScheduledExecutorService`), the test could trigger rendering deterministically. Not a blocker because the test is in `yt-cli` (not gating JaCoCo coverage on `yt-core`) and the sleep budget is generous enough for typical machines.
- **Suggested fix:**
  If C4's injectable constructor is adopted, replace `Thread.sleep` with a direct `render()` call or a `CountDownLatch`-based approach.

## C6 — `ProgressReporter` now implements `ProgressListener` — clean integration

- **Location:** `ProgressReporter.java:29` (`implements ProgressListener, AutoCloseable`)
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-4.1, AC-9.3
- **Reviewer comment:**
  `ProgressReporter` implementing `ProgressListener` means it can be used directly as a listener (for internal wiring) or wrapped by `StderrProgressListener` (for CLI use). The `AutoCloseable` contract ensures the scheduled executor is shut down. The architecture doc's description of `ProgressReporter` as the component that "emits to an injectable `ProgressListener`" is satisfied — `ProgressReporter` *is* a `ProgressListener` that renders to a sink, and the CLI wraps it. Good compositional design.
