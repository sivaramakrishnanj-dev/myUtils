## C1 — AC-4.4 satisfied: `--quiet` suppresses progress via `ProgressListener.NO_OP`

- **Location:** `Cli.java:55`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-4.4 — "WHERE the user passes `--quiet`, the system SHALL suppress all progress output but SHALL NOT suppress errors."
- **Reviewer comment:**
  The implementation is clean and direct: `quiet ? ProgressListener.NO_OP : new StderrProgressListener()`. When `--quiet` is set, the `NO_OP` lambda discards all progress events. Error output flows through the `catch` block's `err.println(report.message())` path, which is completely independent of the listener. AC-4.4 is satisfied in both directions — progress suppressed, errors preserved.

## C2 — AC-5.1 errors visible with `--quiet`: correct

- **Location:** `Cli.java:58–65`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-5.1 — "On any non-success exit, the system SHALL write exactly one human-readable error line to stderr."
- **Reviewer comment:**
  The error pipeline (`catch → ErrorMapper.map → err.println`) is completely decoupled from the progress listener. The `--quiet` flag only controls which `ProgressListener` is constructed; it never touches the error-printing path. Tests `call_givenQuietAndInvalidUrl_stillPrintsErrorToStderr` and `call_givenQuietAndDebugAndInvalidUrl_printsErrorAndStackTrace` confirm this. Well done — the separation of concerns between progress and error output is exactly what the architecture intended.

## C3 — AutoCloseable pattern in `finally` is correct but has a minor gap

- **Location:** `Cli.java:66–70`
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** Clean Code (Martin) — error handling; Effective Java item 9 (prefer try-with-resources)
- **Reviewer comment:**
  The `finally` block uses `instanceof AutoCloseable ac` pattern matching to conditionally close the listener. This is correct: `StderrProgressListener` implements `AutoCloseable`, so it gets closed; `ProgressListener.NO_OP` is a bare lambda that does not, so the `instanceof` check is `false` and no close is attempted. The `catch (Exception ignored)` swallows close failures silently — acceptable here because `ProgressReporter.close()` only shuts down a daemon-thread scheduler and flushes a `PrintWriter`, neither of which should throw in practice.

  However, the `catch (Exception ignored)` variable name `ignored` is good practice (signals intent), but the block swallows the exception without logging. If `close()` ever does fail (e.g., a future `ProgressReporter` implementation that flushes to a file), the failure would be invisible. Consider logging at `DEBUG` level: `LOGGER.debug("Failed to close progress listener", ignored)`.
- **Suggested fix:**
  ```java
  try { ac.close(); } catch (Exception e) { LOGGER.debug("Failed to close progress listener", e); }
  ```

## C5 — `ProgressListener.NO_OP` is not `AutoCloseable` — intentional and correct

- **Location:** `ProgressListener.java:18` (`NO_OP = (b, t) -> {}`)
- **Severity:** Praise
- **Category:** Correctness
- **Spec citation:** *A Philosophy of Software Design* (Ousterhout) — information hiding; Effective Java item 42 (prefer lambdas)
- **Reviewer comment:**
  `NO_OP` is a bare lambda, not an `AutoCloseable`. This is correct by design: there is nothing to close. The `Cli.call()` `finally` block's `instanceof AutoCloseable` check handles this cleanly — `NO_OP` skips the close path. The tester's test 7 (`call_givenQuietAndException_finallyCleansUpNoOpListener`) explicitly verifies this. Good defensive design.

## C6 — Tester's listener-capture limitation with `final YoutubeDownloader` is acceptable

- **Location:** `CliQuietBehaviorTest.java` (all tests)
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** Pinned tenet 4 — SUT must not be mocked
- **Reviewer comment:**
  The tester noted a limitation: because `Cli` constructs the `ProgressListener` internally (line 55), the test cannot directly assert *which* listener was passed to `download()`. The tests work around this by verifying observable behavior: exit code, stderr content, and absence of crashes. This is the right approach — the SUT (`Cli`) is real, the `YoutubeDownloader` is a fake (via `FakeDownloaderFactory`), and the assertions are on externally-observable outcomes.

  The limitation is inherent to the current design where `Cli.call()` constructs the listener inline. A future refactoring could extract a `ProgressListenerFactory` to make the choice testable via injection, but that's over-engineering for a boolean flag. The current tests adequately verify AC-4.4's behavioral contract. Acceptable as-is.
