## C1 — Long multiplication overflow in `assertSufficientFreeSpace`

- **Location:** `OutputWriter.java:112` — `long required = FREE_SPACE_MULTIPLIER * expectedBytes;`
- **Severity:** Major
- **Category:** Correctness
- **Spec citation:** NFR-MIN-DISK-FREE — "2 × expected final file size"; Effective Java item 6 (avoid surprises with primitive arithmetic)
- **Reviewer comment:**
  `FREE_SPACE_MULTIPLIER * expectedBytes` is a `long × long` multiplication. When `expectedBytes > Long.MAX_VALUE / 2` (≈ 4.6 EB), the product silently overflows to a negative value, and the `usable < required` comparison becomes `usable < negative`, which is always `false` — the check passes when it should fail. In practice, no YouTube video is 4.6 EB, so this is not exploitable today. However, the tester's test `assertSufficientFreeSpace_givenVeryLargeExpectedBytes_throwsFilesystemException` passes `Long.MAX_VALUE / 3`, which does overflow (`2 * 3074457345618258602 = 6148914691236517204`, which wraps to a negative). That test passes only because the overflowed negative value happens to be less than `usable` on some platforms — it's a coincidence, not a guarantee. The test at line `Long.MAX_VALUE / 2` also relies on overflow behavior.

  The fix is a single-line overflow guard before the multiplication:
  ```java
  long required = (expectedBytes > Long.MAX_VALUE / FREE_SPACE_MULTIPLIER)
      ? Long.MAX_VALUE
      : FREE_SPACE_MULTIPLIER * expectedBytes;
  ```
  This saturates to `Long.MAX_VALUE` instead of wrapping, which always triggers the insufficient-space path for absurdly large inputs.
- **Suggested fix:** Add the overflow guard above. The tester's two large-value tests will then pass deterministically on all platforms.

## C5 — AC-3.1 CWD default: correct but relies on `Path.of("")`

- **Location:** `OutputWriter.java:77` — `Path dir = config.outputDir().orElse(Path.of(""));`
- **Severity:** Minor
- **Category:** Readability
- **Spec citation:** AC-3.1 — "The system SHALL write all output files to the current working directory when `--output-dir` is not given."
- **Reviewer comment:**
  `Path.of("")` resolves to the current working directory in Java's `Path` API — `Path.of("").resolve("foo.mp4")` produces `foo.mp4` (a relative path that the JVM resolves against CWD). This is correct and the test `deriveOutputPath_givenNeither_usesCwd` verifies it. However, `Path.of("")` is a Java idiom that not every reader knows. A brief inline comment would help:
  ```java
  Path dir = config.outputDir().orElse(Path.of("")); // empty path = CWD
  ```
  Nit-level, but since this is the AC-3.1 implementation point, a comment aids traceability.

## C7 — AC-3.2 `mkdir -p` as side effect of `assertSufficientFreeSpace`

- **Location:** `OutputWriter.java:105–108` — `Files.createDirectories(probeDir)`
- **Severity:** Minor
- **Category:** Design-Gap
- **Spec citation:** AC-3.2 — "WHEN the path does not exist, the system SHALL create it (including parents, `mkdir -p`-equivalent) before writing."
- **Reviewer comment:**
  The `mkdir -p` behavior is implemented inside `assertSufficientFreeSpace`, not as a standalone method. This means directory creation only happens when the caller probes disk space. If a future caller calls `deriveOutputPath` + `assertNotExistsOrForce` but skips `assertSufficientFreeSpace` (e.g., when expected size is unknown), the directory won't be created. The current orchestrator flow always calls `assertSufficientFreeSpace`, so this works today.

  This is a coupling concern, not a bug. The directory-creation responsibility is bundled with the disk-space probe because both need the parent directory to exist. A cleaner separation would be a dedicated `ensureOutputDirectory(Path)` method that both `assertSufficientFreeSpace` and the orchestrator can call independently. However, this is a design preference, not a spec violation — AC-3.2 is satisfied in the current flow. Flagging for awareness.
