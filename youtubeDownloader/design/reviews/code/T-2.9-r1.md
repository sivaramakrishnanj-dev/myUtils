## C1 — `deleteRecursively` wraps `IOException` in unchecked `RuntimeException`

- **Location:** `DownloadContext.java:107` — lambda inside `Files.walk(...).forEach(...)`
- **Severity:** Minor
- **Category:** Reliability
- **Reviewer comment:**
  The `forEach` lambda catches `IOException` and wraps it in a bare `RuntimeException`. If deletion of one file fails mid-walk, the `RuntimeException` propagates out of the stream, but the outer `catch (IOException e)` in `close()` will not catch it — it will escape as an unchecked exception from `close()`. This breaks the idempotent-close contract: a partially-failed cleanup would throw instead of logging a WARN. *Release It!* — stability patterns: never let a cleanup path throw unexpectedly.
- **Suggested fix:**
  Catch `RuntimeException` in `close()` alongside `IOException`, or use an `UncheckedIOException` wrapper and catch that. Alternatively, replace the stream-based walk with an explicit loop that accumulates failures and logs them.

## C2 — `tempFile()` does not guard against path traversal

- **Location:** `DownloadContext.java:68` — `tempFile(String name)`
- **Severity:** Minor
- **Category:** Security
- **Spec citation:** NFR-TEMP-DIR-STRATEGY — "`.part` files land here during the run"
- **Reviewer comment:**
  `tempFile("../escape")` resolves outside `tempDir()`. The tester's `DownloadContextBehaviorTest` explicitly documents this as "internal API only" and verifies the path escapes. While `DownloadContext` is internal to the orchestrator today, the public method signature (`public Path tempFile(String name)`) makes it accessible to any code in the package. A single `normalize()` + starts-with check is cheap insurance against accidental misuse. *A Philosophy of Software Design* — deep modules should protect their own invariants rather than relying on callers.
- **Suggested fix:**
  ```java
  public Path tempFile(String name) {
      Path resolved = tempDir.resolve(name).normalize();
      if (!resolved.startsWith(tempDir)) {
          throw new IllegalArgumentException("name escapes temp directory: " + name);
      }
      return resolved;
  }
  ```

## C3 — `success` field is `volatile` but no concurrent access pattern exists

- **Location:** `DownloadContext.java:33` — `private volatile boolean success`
- **Severity:** Nit
- **Category:** Readability
- **Reviewer comment:**
  The `volatile` qualifier implies cross-thread visibility is needed, but the architecture doc (§ 6) pins the concurrency model as single-threaded per `download()` call. `markSuccess()` and `close()` are called sequentially by the orchestrator on the same thread. The `volatile` is harmless but misleading — a reader wonders "which thread calls `markSuccess()` while another calls `close()`?" *Clean Code* — every keyword should earn its place.
- **Suggested fix:**
  Remove `volatile` unless a cross-thread use case is documented. If the intent is future-proofing for shutdown-hook access, add a comment explaining that.

## C8 — WARN log content not verifiable in tests (no SLF4J backend in yt-core test classpath)

- **Location:** `DownloadContextBehaviorTest.java:175` — comment in `warnOrphanTempDirs_givenOrphanDir_completesNormally`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** AC-10.3
- **Reviewer comment:**
  The tester correctly notes that WARN log content cannot be asserted because yt-core has no SLF4J backend in test scope (by design — the library module delegates backend choice to the CLI). The test verifies the method completes without exception and the orphan is not deleted, which is the behavioral contract. However, the WARN message is an AC-10.3 requirement. A lightweight approach: add `slf4j-test` (from `org.slf4j:slf4j-test`) as a test-scoped dependency in yt-core, which provides an in-memory `TestLogger` that captures log events. This would let the tester assert the WARN message content without coupling to a real backend. Not blocking — the behavioral contract is tested; the log content is a quality gap.
- **Suggested fix:**
  Consider adding `slf4j-test` as a test-scoped dependency in a future task (or as a cross-cutting improvement in M5). Not required for T-2.9 resolution.
