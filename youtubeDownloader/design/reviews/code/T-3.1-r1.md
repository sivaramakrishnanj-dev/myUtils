## C1 — Process not destroyed on exception paths

- **Location:** `FfmpegMuxer.java:82–100` — `probeVersion()` try block
- **Severity:** Major
- **Category:** Reliability
- **Spec citation:** ADR-0003 (ProcessBuilder resource hygiene); Release It! — stability pattern: close resources on failure
- **Reviewer comment:**
  The `Process` object created at line 82 is never explicitly destroyed. If `reader.readLine()` throws an `IOException`, or if `process.waitFor()` throws `InterruptedException`, the child process is not terminated. While `ffmpeg -version` exits quickly on its own in the happy path, on the `InterruptedException` path the process may linger as a zombie until GC finalizes it. This is the same component that will later run long-lived mux/transcode subprocesses (T-3.2..T-3.6), so establishing the `destroy()` discipline now prevents a copy-paste omission later.
- **Suggested fix:**
  Wrap the process lifecycle in a try-finally:
  ```java
  Process process = new ProcessBuilder(ffmpegBinaryPath, "-version")
          .redirectErrorStream(true)
          .start();
  try {
      try (BufferedReader reader = new BufferedReader(
              new InputStreamReader(process.getInputStream(), StandardCharsets.UTF_8))) {
          firstLine = reader.readLine();
      }
      exitCode = process.waitFor();
  } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
      throw new FfmpegException(/* ... */, e);
  } finally {
      process.destroy();
  }
  ```
  `Process.destroy()` is a no-op if the process has already exited, so calling it unconditionally is safe.

## D1 — `YoutubeDownloaderException` is unchecked but spec says checked

- **Location:** `YoutubeDownloaderException.java:15` — `extends RuntimeException`
- **Severity:** Discussion
- **Category:** Discussion
- **Spec citation:** `04-apis.md` § 3.2.2: "All exceptions are **checked**."
- **Reviewer comment:**
  `04-apis.md` § 3.2.2 states: "All exceptions are **checked**. The library's contract is that `download()` either returns a `DownloadResult` or throws a specific subtype of `YoutubeDownloaderException`. No `RuntimeException` subtypes are thrown from normal failure paths." However, `YoutubeDownloaderException extends RuntimeException` (unchecked). The class Javadoc explains the rationale: "Unchecked... callers catch at the top-level orchestration boundary, not at every intermediate call site." This is a pre-existing design decision from T-1.9, not a T-3.1 issue. The code is internally consistent (all subtypes extend the same sealed base), but the spec text disagrees with the implementation.
- **Suggested amendment kind:** ac-update (align `04-apis.md` § 3.2.2 prose with the actual `RuntimeException` choice, or vice versa)
- **Impact on this review's verdict:** none — this is a spec gap, not a code defect in T-3.1.
