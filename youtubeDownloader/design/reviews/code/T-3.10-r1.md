## C1 — Correct decision: no production change needed

- **Location:** `YoutubeDownloader.java:172–295` (existing `downloadAudioOnly` method)
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-13.5, INV-10
- **Reviewer comment:**
  The implementer correctly identified that the existing code structure already satisfies AC-13.5 and INV-10. The `downloadAudioOnly` method's M4A branch (the `else` block at line ~275) never calls `muxerFactory.apply(request)` — it downloads directly to `.part` and moves to `.m4a`. The `muxerFactory` is only invoked in the MP3 branch and in `downloadVideoAudio`. This means M4A audio-only paths have *always* skipped ffmpeg since T-2.10 landed. The right engineering call was to add characterization tests proving this invariant rather than introducing unnecessary code changes.

## C2 — Throwing-factory test pattern is clean and effective

- **Location:** `FfmpegMuxerSkipBehaviorTest.java:47`
- **Severity:** Praise
- **Category:** Testing
- **Spec citation:** AC-13.5
- **Reviewer comment:**
  The `THROWING_FACTORY` constant + `AtomicBoolean` witness pattern is a textbook way to prove a code path is *not* taken. It's stronger than a mock-verify-never because it fails loudly at the point of violation rather than at assertion time. The SUT (`YoutubeDownloader`) is real — only external HTTP is faked via OkHttp interceptors. Clean Code: tests are readable, intention-revealing, and each tests exactly one thing.

## C3 — Positive-control tests prove the factory IS called when needed

- **Location:** `FfmpegMuxerSkipBehaviorTest.java:119–133`
- **Severity:** Praise
- **Category:** Testing
- **Spec citation:** INV-10
- **Reviewer comment:**
  Tests `download_mp3AudioOnly_withThrowingFactory_throwsBecauseFactoryIsCalled` and `download_videoAudio_withThrowingFactory_throwsBecauseFactoryIsCalled` are essential positive controls. They prove the throwing-factory pattern is not vacuously passing — the factory *is* invoked on paths that need ffmpeg. Without these, the M4A skip tests could pass simply because the factory is broken. Good test design (A Philosophy of Software Design — tests should verify both the positive and negative paths of a decision).

## C5 — Minor duplication between FfmpegMuxerSkipTest and FfmpegMuxerSkipBehaviorTest

- **Location:** `FfmpegMuxerSkipTest.java` (entire file) vs `FfmpegMuxerSkipBehaviorTest.java:88–97`
- **Severity:** Minor
- **Category:** Reuse
- **Reviewer comment:**
  `FfmpegMuxerSkipTest.download_audioOnlyM4a_succeedsWithoutInvokingFfmpeg()` is functionally identical to `FfmpegMuxerSkipBehaviorTest.download_m4aAudioOnly_withThrowingFactory_succeedsWithoutInvokingFactory()`. Both use a throwing factory, both assert `.m4a` output exists. The characterization test in `FfmpegMuxerSkipTest` was likely the implementer's initial proof; the behavior test suite in `FfmpegMuxerSkipBehaviorTest` subsumes it entirely.
- **Suggested fix:** Consider removing `FfmpegMuxerSkipTest.java` since `FfmpegMuxerSkipBehaviorTest` covers the same assertion plus five additional scenarios. Not blocking — the duplication is harmless and both tests are fast.
