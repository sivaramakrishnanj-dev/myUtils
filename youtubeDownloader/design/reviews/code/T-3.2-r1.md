## C1 — Unbounded stderr capture could exhaust heap on pathological ffmpeg output

- **Location:** `FfmpegMuxer.java:131–133` — `reader.lines().reduce((a, b) -> a + "\n" + b)`
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** AC-13.4, NFR-FFMPEG-STDERR-LINES = 20
- **Reviewer comment:**
  The current implementation reads all of stderr into a single `String` via `reduce`. For a normal mux this is fine — ffmpeg emits a handful of lines at `-loglevel error`. However, under `-loglevel info` (debug mode), ffmpeg can emit thousands of lines of per-frame progress. This is a known predecessor to T-3.4 (ring-buffer capture, last 20 lines), so the current read-to-EOF approach is acceptable for this task. Flagging as Minor because the risk is bounded by the fact that T-3.4 is the immediate next task and will replace this with a ring buffer. If T-3.4 were not planned, this would be Major.
- **Suggested fix:**
  No action needed now — T-3.4 will replace this with a bounded ring buffer of `NFR-FFMPEG-STDERR-LINES = 20` lines.

## C2 — stderr concatenation via `reduce` is O(n²) in line count

- **Location:** `FfmpegMuxer.java:133` — `reader.lines().reduce((a, b) -> a + "\n" + b)`
- **Severity:** Nit
- **Category:** Performance
- **Reviewer comment:**
  `reduce` with string concatenation is O(n²) — each intermediate result allocates a new `String`. A `Collectors.joining("\n")` or `StringBuilder` would be O(n). In practice, stderr at `-loglevel error` is a few lines, so this is negligible. T-3.4's ring buffer will replace this entirely. Noting for awareness, not action.
- **Suggested fix:**
  `reader.lines().collect(Collectors.joining("\n"))` — but T-3.4 will supersede this anyway.

## C11 — Test: conditional real-ffmpeg test uses assumeThat correctly

- **Location:** `FfmpegMuxerMuxBehaviorTest.java:157–172` — `mux_givenRealFfmpegWithEmptyParts_throwsFfmpegException`
- **Severity:** Minor
- **Category:** Testing
- **Reviewer comment:**
  The conditional real-ffmpeg test correctly uses `assumeThat` to skip when ffmpeg is not on PATH. However, the skip pattern (`assumeThat(false).as("...").isTrue()`) is slightly awkward — it works but reads oddly. A more idiomatic approach would be `assumeThat(e).as("ffmpeg not on PATH").isNull()` or simply `org.junit.jupiter.api.Assumptions.assumeTrue(false, "ffmpeg not on PATH")`. This is consistent with the same pattern used in `FfmpegMuxerBehaviorTest` (T-3.1 tests), so it's a pre-existing style choice. Not worth changing in isolation.
- **Suggested fix:**
  Consider standardizing on `Assumptions.assumeTrue(false, "ffmpeg not on PATH")` in a future cleanup pass across all ffmpeg test classes.
