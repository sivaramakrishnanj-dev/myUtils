## C1 — Unbounded stderr capture (same pattern as T-3.2 mux)

- **Location:** `FfmpegMuxer.java:183–185` — `reader.lines().reduce((a, b) -> a + "\n" + b)`
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** AC-13.4, NFR-FFMPEG-STDERR-LINES = 20
- **Reviewer comment:**
  Same unbounded stderr read-to-EOF as the `mux()` method reviewed in T-3.2-r1 C1. Under `-loglevel info` (debug mode), ffmpeg can emit thousands of lines during a transcode (per-frame progress). This is acceptable because T-3.4 (ring-buffer capture, last 20 lines) is the immediate next task and will replace this with a bounded buffer. If T-3.4 were not planned, this would be Major.
- **Suggested fix:**
  No action needed now — T-3.4 will replace this with a bounded ring buffer of `NFR-FFMPEG-STDERR-LINES = 20` lines.

## C2 — stderr concatenation via `reduce` is O(n²) in line count

- **Location:** `FfmpegMuxer.java:185` — `reader.lines().reduce((a, b) -> a + "\n" + b)`
- **Severity:** Nit
- **Category:** Performance
- **Reviewer comment:**
  Same O(n²) string concatenation pattern as `mux()` (T-3.2-r1 C2). `Collectors.joining("\n")` would be O(n). Negligible in practice at `-loglevel error`; T-3.4's ring buffer will supersede this entirely. Noting for consistency with the T-3.2 review, not for action.
- **Suggested fix:**
  `reader.lines().collect(Collectors.joining("\n"))` — but T-3.4 will supersede.

- **Reviewer comment:**
