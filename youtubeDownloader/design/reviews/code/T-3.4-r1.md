## C1 — `captureLastLines` does not guard against `maxLines ≤ 0`

- **Location:** `FfmpegMuxer.java:253` — `captureLastLines(InputStream stream, int maxLines)`
- **Severity:** Minor
- **Category:** Correctness
- **Spec citation:** NFR-FFMPEG-STDERR-LINES = 20 (the only production caller passes `FFMPEG_STDERR_LINES = 20`)
- **Reviewer comment:**
  When `maxLines` is 0, `ring.size() == 0` is true before every `addLast`, so `pollFirst` runs on every iteration but the deque auto-grows — effectively no cap. When `maxLines` is negative, `ring.size() == -1` is never true, so no eviction occurs — all lines are kept. Both cases silently degrade to "capture everything", which is the opposite of the ring-buffer contract. The tester correctly documented this edge case in two tests (`captureLastLines_givenZeroMaxLines_returnsAllLines`, `captureLastLines_givenNegativeMaxLines_returnsAllLines`).

  In production this is unreachable because the only caller passes the constant `FFMPEG_STDERR_LINES = 20`. The method is package-private, not public API. This is a defensive-coding nit, not a correctness bug in the current call graph.

  *Clean Code* (Martin) — defensive programming: a method's contract should hold for all inputs in its declared type, not just the ones the current caller happens to pass. An `IllegalArgumentException` on `maxLines < 1` would make the contract explicit and prevent future misuse.
- **Suggested fix:**
  Add a guard clause at the top of `captureLastLines`:
  ```java
  if (maxLines < 1) {
      throw new IllegalArgumentException("maxLines must be ≥ 1, got " + maxLines);
  }
  ```
  Update the two edge-case tests to assert `IllegalArgumentException` instead of "returns all lines".

## C3 — Characterization test uses raw `assert` instead of AssertJ

- **Location:** `FfmpegMuxerStderrCaptureTest.java:42–53`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** —
- **Reviewer comment:**
  The implementer's characterization test uses Java's `assert` keyword inside a `satisfies` lambda:
  ```java
  assert !msg.contains("stderr line " + i + "\n")
          || (i == 1 && !msg.contains("stderr line 1\n"))
          : "Expected line " + i + " to be dropped";
  ```
  This has two problems: (a) `assert` is a no-op unless `-ea` is enabled in the JVM — if Surefire doesn't pass `-ea`, the test silently passes without checking anything; (b) the condition for `i == 1` is a tautology (`!msg.contains(X) || (i==1 && !msg.contains(X))` simplifies to `!msg.contains(X)` when `i==1`), making the logic confusing.

  The behavior test (`FfmpegMuxerStderrCaptureBehaviorTest`) covers the same scenario correctly with AssertJ's `assertThat(lines).doesNotContain(...)` / `.contains(...)`. The characterization test is therefore redundant in coverage but should still use AssertJ for consistency and reliability.

  *Google Code Review Guide* — test assertions should use the project's assertion library uniformly.
- **Suggested fix:**
  Replace the `assert` statements with AssertJ assertions matching the pattern in the behavior test. Or, since the behavior test already covers this scenario with stronger assertions, consider whether the characterization test adds value beyond the behavior test.

## C4 — `captureLastLines` helper is well-factored and reused across both methods

- **Location:** `FfmpegMuxer.java:248–265` — `captureLastLines`; callers at lines 171 and 227
- **Severity:** Praise
- **Category:** Reuse
- **Spec citation:** AC-13.4
- **Reviewer comment:**
  The previous implementation in T-3.2 and T-3.3 used inline `reader.lines().reduce((a, b) -> a + "\n" + b).orElse("")` — unbounded, O(n²) string concatenation, and duplicated across `mux` and `transcodeMp3`. T-3.4 extracts a single `captureLastLines` helper with a bounded `ArrayDeque` ring buffer, used by both methods. The refactoring is clean: the helper is package-private (testable from the same package), stateless, and its contract is documented in the Javadoc. Good application of DRY and *A Philosophy of Software Design* (Ousterhout) — the helper is a deep module with a simple interface.

## C7 — `probeVersion` correctly untouched — `redirectErrorStream(true)` merges stderr into stdout

- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-13.1, AC-13.2, AC-13.3
- **Reviewer comment:**
  `probeVersion()` uses `redirectErrorStream(true)`, which merges stderr into stdout for the version probe. The `captureLastLines` ring buffer is correctly NOT applied to `probeVersion` — it's only for `mux` and `transcodeMp3` where stderr is the error-surfacing channel (AC-13.4). Good boundary awareness.

## C8 — `mux()` success path drains stderr silently

- **Location:** `FfmpegMuxerStderrCaptureBehaviorTest.java:148–158` — `mux_givenSuccessWithStderr_doesNotThrow`
- **Severity:** Praise
- **Category:** Reliability
- **Spec citation:** AC-13.4
- **Reviewer comment:**
  The test verifies that when ffmpeg exits 0 but still writes to stderr (common — ffmpeg emits codec info even at `-loglevel error`), the stderr is drained silently and no exception is thrown. This prevents a subtle deadlock: if stderr isn't drained and the pipe buffer fills, ffmpeg blocks on write and the process hangs. The `captureLastLines` call before `waitFor()` ensures the stream is fully consumed regardless of exit code. Correct ordering.
