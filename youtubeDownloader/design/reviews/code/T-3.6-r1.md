## C1 — Timeout constant correctly pins NFR-FFMPEG-INVOCATION-TIMEOUT = 600

- **Location:** `FfmpegMuxer.java:67` — `FFMPEG_TIMEOUT_SECONDS = 600`
- **Severity:** Praise

  The constant is `static final long`, package-visible for test assertion, and its Javadoc cites both the NFR and the task ID. Single source of truth — the public constructors delegate to the package-private ctor with this value. Clean.

## C2 — Timeout progression matches spec: SIGTERM → 5s grace → SIGKILL → FfmpegException

- **Location:** `FfmpegMuxer.java:202–210` (mux) and `FfmpegMuxer.java:271–279` (transcodeMp3)
- **Severity:** Praise
- **Category:** Correctness
- **Spec citation:** ADR-0003 § Decision: "on timeout, sends SIGTERM, waits 5 s, sends SIGKILL per the shutdown model in `02-architecture.md` § 5"; `02-architecture.md` § 5.1 step 2
- **Reviewer comment:**
  Both methods follow the exact sequence: `process.waitFor(timeoutSeconds, SECONDS)` → on `false`: `process.destroy()` (SIGTERM) → `process.waitFor(SHUTDOWN_GRACE_SECONDS, SECONDS)` → `process.destroyForcibly()` (SIGKILL) → throw `FfmpegException` with "timeout" in the message. This matches the spec's shutdown model and reuses the same `SHUTDOWN_GRACE_SECONDS = 5` constant from T-3.5. The `FfmpegException` carries `exitCode() == 60` per `cli-exit-codes.md`. *Release It!* (Nygard) — textbook timeout + escalation pattern.

## C3 — Package-private constructor for test injection is the right testability pattern

- **Location:** `FfmpegMuxer.java:99–102` — `FfmpegMuxer(String ffmpegBinaryPath, long timeoutSeconds)`
- **Severity:** Praise
- **Category:** Testing
- **Spec citation:** AC-11.1 (offline testability)
- **Reviewer comment:**
  The 3-arg package-private ctor allows tests to inject a 1-second timeout with a fake script, keeping test execution fast (≤ 2s per test) while production uses the 600s default. The constructor chain (`public()` → `public(String)` → `package-private(String, long)`) is clean and avoids exposing the timeout parameter in the public API. This is the same pattern used for `ffmpegBinaryPath` injection in T-3.1.

## C4 — Timeout block duplicated between mux() and transcodeMp3()

- **Location:** `FfmpegMuxer.java:202–210` and `FfmpegMuxer.java:271–279`
- **Severity:** Minor
- **Category:** Readability
- **Spec citation:** *Refactoring* (Fowler) — "Duplicated Code" smell
- **Reviewer comment:**
  The 11-line timeout-check-and-kill block is identical in both methods. This duplication is pre-existing from T-3.2/T-3.3 (the process-launch + stderr-capture + exit-check pattern was already duplicated); T-3.6 adds the timeout block to both copies. The two methods differ only in command construction and error-message prefix ("mux" vs "transcode"), so extracting a `runFfmpeg(List<String> command, String operationName)` helper would consolidate ~30 lines of shared logic. Not blocking — the methods are short and the duplication is localized — but worth considering as the class grows (T-3.7 adds `--ffmpeg-location` which touches both paths again).
- **Suggested fix:**
  Extract a private `runFfmpegProcess(List<String> command, String operationLabel)` method that handles process start, `LIVE_PROCESSES` registration, stderr capture, timeout check, exit-code check, and cleanup. Each public method builds its command list and delegates. Optional — author decides.

## C5 — Test coverage is thorough: both methods, both outcomes, cleanup, constant, exit code

- **Location:** `FfmpegMuxerTimeoutTest.java` (1 test) + `FfmpegMuxerTimeoutBehaviorTest.java` (8 tests)
- **Severity:** Praise
- **Category:** Testing
- **Spec citation:** AC-11.1, CT-EXIT-60, NFR-FFMPEG-INVOCATION-TIMEOUT
- **Reviewer comment:**
  9 tests cover: mux timeout → exception with "timeout" message (×2 — characterization + behavior), transcodeMp3 timeout → exception, mux within timeout → no exception, transcodeMp3 within timeout → no exception, liveProcesses empty after timeout (INV-8), default constant == 600 (×2), and exit code == 60 (CT-EXIT-60). ## C6 — Tester's fix to characterization test is well-motivated

- **Location:** `FfmpegMuxerTimeoutTest.java:30` — `exec 2>/dev/null\nsleep 2`
- **Severity:** Praise
- **Category:** Testing
- **Spec citation:** AC-11.1 (offline testability), NFR-UNIT-TEST-RUNTIME-BUDGET (30s total)
- **Reviewer comment:**
  The original characterization test used `sleep 3600` which would have blocked `captureLastLines` on the open stderr pipe indefinitely — the timeout would never fire because the main thread was stuck reading stderr, not in `waitFor`. Closing stderr with `exec 2>/dev/null` before sleeping lets `captureLastLines` return immediately, and reducing sleep to 2s (with a 1s timeout) keeps the test well within the 30s unit-test budget. Good diagnosis of a subtle interaction between the stderr-capture thread model and the timeout mechanism.

## C7 — No validation on timeoutSeconds in package-private constructor

- **Location:** `FfmpegMuxer.java:99–102`
- **Severity:** Nit
- **Category:** API-Design
- **Spec citation:** *Effective Java* Item 49 — check parameters for validity
- **Reviewer comment:**
  A zero or negative `timeoutSeconds` would cause `waitFor(0, SECONDS)` to return `false` immediately, triggering the kill sequence on a process that just started. The ctor is package-private and only called by tests with known-good values, so the blast radius is minimal. A one-line guard (`if (timeoutSeconds <= 0) throw new IllegalArgumentException(...)`) would make the contract explicit.
- **Suggested fix:**
  Add `if (timeoutSeconds <= 0) { throw new IllegalArgumentException("timeoutSeconds must be positive"); }` in the 3-arg constructor. Author decides.
