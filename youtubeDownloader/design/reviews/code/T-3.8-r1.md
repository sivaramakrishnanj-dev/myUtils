## C3 — OutputWriter checks run BEFORE download, not before mux

- **Location:** `YoutubeDownloader.downloadVideoAudio()` lines 185–192
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** AC-3.6, state-machine `WRITING_OUTPUTS → TERMINATED` (exit 50)
- **Reviewer comment:**
  `assertNotExistsOrForce` and `assertSufficientFreeSpace` run *before* the stream downloads begin. This is actually **better** than the state machine's literal placement (which shows `WRITING_OUTPUTS → TERMINATED` for exit 50/70) — it fails fast before wasting bandwidth. However, the free-space check uses `videoFormat.contentLength().orElse(0L) + audioFormat.contentLength().orElse(0L)` which underestimates the required space: it doesn't account for the muxed output file that will coexist with the `.part` files during mux. `NFR-MIN-DISK-FREE` says "2× expected final file size" — the current code passes `expectedBytes` (sum of parts) to `assertSufficientFreeSpace`, which internally multiplies by 2, so the effective check is `2 × (video + audio)`. Since the muxed MP4 is roughly `video + audio` in size (stream-copy mux), the 2× multiplier covers the coexistence window. Acceptable.
- **Suggested fix:**
  No code change needed. Consider adding a comment explaining why the 2× multiplier is sufficient for the coexistence of `.part` files + muxed output.

## C7 — `DownloadContext.close()` swallows `FfmpegException` on mux failure path

- **Location:** `YoutubeDownloader.downloadVideoAudio()` lines 197–213 (try-with-resources)
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** INV-6 (context retained on failure)
- **Reviewer comment:**
  When `mux()` throws `FfmpegException`, the try-with-resources calls `DownloadContext.close()`. Since `markSuccess()` was not called, `close()` retains the temp dir (correct per INV-6) and logs at INFO. However, if `close()` itself threw an `IOException` (e.g., filesystem error during the "is empty?" check), it would be added as a suppressed exception on the `FfmpegException`. This is standard Java try-with-resources behavior and is fine — the primary exception propagates. Just noting that the `close()` method's `catch (IOException)` already handles this by logging at WARN and not re-throwing. Correct.
- **Suggested fix:**
  None needed. The implementation is correct.

## C10 — `FakeDownloaderFactory` uses `Files.createTempFile` without `@TempDir`

- **Location:** `FakeDownloaderFactory.fakeFfmpegPath()` line 63
- **Severity:** Minor
- **Category:** Testing
- **Reviewer comment:**
  The fake ffmpeg script is created via `Files.createTempFile("fake-ffmpeg-", ".sh")` with `deleteOnExit()`. This works but is slightly fragile — `deleteOnExit` is JVM-global and doesn't clean up if the JVM crashes. The `YoutubeDownloaderFlowABehaviorTest` uses `@TempDir` for its fake ffmpeg, which is the better pattern. *Clean Code* — prefer test-framework lifecycle management over manual cleanup.
- **Suggested fix:**
  Consider refactoring `FakeDownloaderFactory` to accept a `Path tempDir` parameter and create the script there, matching the pattern in the behavior tests. Low priority — the current approach works and `deleteOnExit` is adequate for test processes.

## C11 — `FakeDownloaderFactory.fakeFfmpegPath()` uses `touch` instead of writing bytes

- **Location:** `FakeDownloaderFactory.java` line 72 (`touch "$OUTPUT"`)
- **Severity:** Minor
- **Category:** Testing
- **Reviewer comment:**
  The fake ffmpeg in `FakeDownloaderFactory` uses `touch "$OUTPUT"` for mux/transcode, creating a 0-byte file. The fake in `YoutubeDownloaderFlowABehaviorTest` uses `printf '\x00\x01\x02\x03' > "$OUTPUT"`, creating a 4-byte file. Both work because `OutputWriter` doesn't validate file content. However, the `touch` approach means `Files.exists(result.videoPath().get())` passes but `Files.size(...)` would be 0. If a future test asserts non-zero size, the `FakeDownloaderFactory` version would break. Minor inconsistency.
- **Suggested fix:**
  Align `FakeDownloaderFactory` to write a few bytes like the behavior test's fake. Low priority.
