## C1 — `parseAudioFormat` throws `UrlParseException` for invalid `--audio-format` value

- **Location:** `Cli.java:147` — `parseAudioFormat()`
- **Severity:** Minor
- **Category:** API-Design
- **Spec citation:** AC-5.2 — exit code `2` is for "argument / URL parse error"
- **Reviewer comment:**
  Using `UrlParseException` for an invalid `--audio-format` value is semantically acceptable since AC-5.2 maps all argument errors to exit code `2`. However, the error message prefix will be `Error: args:` which is correct. The class name `UrlParseException` is slightly misleading for a non-URL argument error — but since the exception hierarchy maps by exit code (not by name), and the user-facing message is clear (`--audio-format must be 'm4a' or 'mp3', got: <value>`), this is a naming nit rather than a correctness issue. The tester notes that a CLI-level `--audio-format invalid` test belongs in `yt-cli` module — acceptable scope deferral.
- **Suggested fix:**
  Consider renaming to `ArgumentException` in a future task, or accept as-is since exit code mapping is correct.

## C2 — MP3 path: `Files.delete(audioPart)` inside try-with-resources may mask `FfmpegException`

- **Location:** `YoutubeDownloader.java:262` — `Files.delete(audioPart)` in MP3 branch
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** INV-6 (context retained on failure)
- **Reviewer comment:**
  If `transcodeMp3` succeeds but `Files.delete(audioPart)` throws `IOException`, the catch block wraps it as `FilesystemException("Failed to delete audio.part after transcode")`. This is correct — the `.mp3` output file was already written successfully by ffmpeg, so the download *did* succeed from the user's perspective. The `.part` file is inside `.yt-tmp/` which `DownloadContext.close()` would clean anyway on `markSuccess()`. The `Files.delete` call is therefore redundant (the `DownloadContext` recursive delete handles it), but not harmful — it's an eager cleanup. The `IOException` catch wrapping into `FilesystemException` means the user sees exit `70` for a non-critical cleanup failure even though the output file exists. This is a minor UX gap but not a correctness bug — the `.mp3` is on disk.
- **Suggested fix:**
  Move `Files.delete(audioPart)` after `ctx.markSuccess()` or remove it entirely (let `DownloadContext.close()` handle it). Alternatively, catch the `IOException` from `delete` specifically and log at WARN instead of throwing. Low priority — the current behavior is safe.

## C3 — AC-2.5 interpretation: `--audio-format mp3` without `--audio-only` implies audio-only with WARN

- **Location:** `Cli.java:93–96`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-2.5 — "IF `--audio-only` is combined with `--max-height` OR any other video-specific flag, THEN the system SHALL log a warning naming the ignored flag but SHALL NOT fail."
- **Reviewer comment:**
  The implementer's interpretation is reasonable and well-documented: `--audio-format mp3` without `--audio-only` is treated as implying `--audio-only` with a WARN log. AC-2.5 addresses the reverse case (audio-only + video flags), but the spirit is the same — conflicting flags produce a warning, not a failure. The WARN message is clear: `"--audio-format mp3 implies --audio-only; treating as audio-only (AC-2.4)"`. Good defensive UX.
