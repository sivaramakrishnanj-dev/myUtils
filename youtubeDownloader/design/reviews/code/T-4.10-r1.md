## C3 — `handleThumbnail` catches `NetworkException` from empty-list path via `ThumbnailDownloader.pickBest`

- **Location:** `YoutubeDownloader.java:272–285` (`handleThumbnail`)
- **Severity:** Minor
- **Category:** Observability
- **Spec citation:** AC-10.2 (INFO on every external boundary call)
- **Reviewer comment:**
  When `thumbnails` is null or empty, the method logs WARN and returns `Optional.empty()` — correct partial-success. However, the WARN message `"No thumbnails available in player response"` is emitted *before* calling `thumbnailDownloader.download(...)`, so the actual download INFO log from `ThumbnailDownloader` is never reached. This is fine for the empty-list case. But if `ThumbnailDownloader.pickBest` throws `NetworkException("No thumbnails available")` (which it does for empty lists), that exception would be caught by the `catch (NetworkException e)` block and logged as `"Thumbnail download failed (partial success)"` — a slightly misleading message for the "no thumbnails in response" case vs. an actual network failure. The current null/empty guard at line 274 prevents this from happening in practice, so this is cosmetic only.
- **Suggested fix:**
  No change required — the guard is correct. This is informational.

## C4 — Transcript file write IOException caught as partial success

- **Location:** `YoutubeDownloader.java:255–259` (`catch (IOException e)` in `handleTranscript`)
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** 02-architecture.md § 3 (exit code 70 for filesystem errors)
- **Reviewer comment:**
  When `Files.writeString(srtPath, ...)` or `Files.writeString(txtPath, ...)` throws `IOException`, the code catches it and returns partial success (WARN + empty paths). This is a reasonable choice for the transcript side-effect, but it differs from the architecture's exit-code-70 path for filesystem errors. The architecture's failure matrix (§ 3) maps filesystem `IOException` to exit 70 via `FilesystemException`. The partial-success discipline in § 4.3 applies to *network* failures of caption/thumbnail downloads, not filesystem writes. That said, the architecture note in § 4.3 says "a caption-fetch failure is reported as a warning" — the write failure is arguably a different category. In practice, a write failure here (disk full, permissions) would silently lose the transcript without surfacing the filesystem error to the user.
- **Suggested fix:**
  Consider re-throwing as `FilesystemException` for write failures (not network failures) to match the exit-70 contract. However, this is a borderline case — the transcript is a side-effect of the main download, and the user still gets their media file. If the team prefers partial-success for all transcript failures (network + filesystem), document that decision. Not blocking resolution.

## C6 — 7-arg constructor + backward-compatible overloads

- **Location:** `YoutubeDownloader.java:44–90` (constructors)
- **Severity:** Nit
- **Category:** API-Design
- **Spec citation:** Effective Java Item 1 (static factories over constructors)
- **Reviewer comment:**
  Four constructors (7-arg, 5-arg, 4-arg, 2-arg) is a growing telescope. The `create()` factory is the production path, and tests use the 7-arg directly — both are clean. The backward-compatible overloads (5-arg, 4-arg, 2-arg) keep existing tests compiling without modification. This is acceptable for an internal library class. If the constructor count grows further in M5, consider a builder or collapsing to just 7-arg + `create()`.
