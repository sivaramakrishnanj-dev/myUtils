## C1 — Missing attribute → uncaught NumberFormatException

- **Location:** `CaptionConverter.java:42–43` — `Double.parseDouble(el.getAttribute("start"))` / `el.getAttribute("dur")`
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** AC-6.1 (parse timedtext XML)
- **Reviewer comment:**
  If a `<text>` element is missing the `start` or `dur` attribute, `getAttribute()` returns `""` and `Double.parseDouble("")` throws `NumberFormatException`. This propagates as an uncaught runtime exception rather than the expected `InnerTubeParseException` (exit 11). In practice YouTube always provides these attributes, and the spec does not mandate defensive handling of malformed timedtext beyond "malformed XML → InnerTubeParseException". However, wrapping the per-cue parse in a try-catch for `NumberFormatException` (re-throwing as `InnerTubeParseException`) would unify the error path. Downgraded from Major because the spec's "malformed XML" language is ambiguous on whether attribute-level issues count, and real YouTube responses always include both attributes.
- **Suggested fix:**
  Wrap the per-element extraction in a try-catch:
  ```java
  try {
      long startMs = Math.round(Double.parseDouble(el.getAttribute("start")) * 1000);
      long durationMs = Math.round(Double.parseDouble(el.getAttribute("dur")) * 1000);
      ...
  } catch (NumberFormatException e) {
      throw new InnerTubeParseException("Invalid start/dur in <text> element at index " + i, e);
  }
  ```

## C2 — Entity decode order: `&amp;` first is correct but fragile

- **Location:** `CaptionConverter.java:72` — `result.replace("&amp;", "&")` as first replacement
- **Severity:** Nit
- **Category:** Readability
- **Spec citation:** AC-6.3
- **Reviewer comment:**
  Replacing `&amp;` first is the correct order (prevents double-decode of `&amp;lt;` → `&lt;` → `<`). A brief inline comment explaining *why* `&amp;` must be first would help future maintainers. This is a style preference backed by Clean Code's "explain intent" principle — the ordering is non-obvious.
- **Suggested fix:**
  ```java
  // &amp; MUST be decoded first to prevent double-decode (e.g., &amp;lt; → &lt; → <)
  result = result.replace("&amp;", "&");
  ```

## C7 — `DocumentBuilderFactory` created per call — acceptable for correctness

- **Location:** `CaptionConverter.java:52` — `DocumentBuilderFactory.newInstance()` inside `parseDocument`
- **Severity:** Minor
- **Category:** Performance
- **Reviewer comment:**
  A new `DocumentBuilderFactory` is created on every `parseXml` call. `DocumentBuilderFactory` is not thread-safe, so this is the *correct* approach for a static method. The alternative (a static factory with per-call `newDocumentBuilder()`) is safe only if the factory is configured once and never mutated — which is true here but adds subtle thread-safety reasoning. The current approach is simpler and correct. Transcript parsing is not a hot path (called once per video), so the allocation cost is negligible. Flagging only for awareness — no change needed.
- **Suggested fix:** None required. Current approach is correct.
