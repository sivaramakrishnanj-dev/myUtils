## C1 — `toTxt` returns `String` but architecture says `PlainTextTranscript`

- **Location:** `CaptionConverter.java:36` — `public static String toTxt(List<CaptionCue> cues)`
- **Severity:** Minor
- **Category:** Spec-Adherence
- **Spec citation:** `02-architecture.md` § 1.2 — "Converts raw timedtext XML … into two in-memory products: an `SrtDocument` … and a `PlainTextTranscript`"
- **Reviewer comment:**
  The architecture doc states `CaptionConverter` produces a `PlainTextTranscript` as its second product. The current `toTxt` returns a raw `String`. The `PlainTextTranscript` record exists but is disconnected from the converter. This is a minor cohesion gap — the record's `toString()` duplicates the `String.join("\n", lines)` logic already in `toTxt`. Downstream orchestrator code will need to decide whether to wrap the result or call `toTxt` directly.
- **Suggested fix:**
  Consider returning `PlainTextTranscript` from `toTxt` (or add a `toPlainTextTranscript` method that wraps the lines list). Alternatively, if the current `String`-returning API is intentional for simplicity, document the deviation. Not blocking — the behavior is correct and the record is tested independently.

## C4 — Empty-string cue collapse is spec-correct

- **Location:** `CaptionConverter.java:40` — `cues.get(i + 1).text().startsWith(text)`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** § 2.8 — "collapse if the next cue's text starts with the previous cue's text"
- **Reviewer comment:**
  `"".startsWith("")` is `true` in Java, so an empty-string cue followed by any cue is collapsed. The tester documented this as correct per spec wording — agreed. The spec says "starts with the previous cue's text" without an exception for empty strings. The behavior is deterministic and tested (`toTxt_givenEmptyTextCue_collapsedBecauseEmptyIsPrefix`).

## C6 — `toTxt` does not null-check the input list

- **Location:** `CaptionConverter.java:36`
- **Severity:** Nit
- **Category:** Correctness
- **Reviewer comment:**
  `toTxt(null)` would throw `NullPointerException` at `cues.size()`. The upstream `parseXml` never returns null (returns empty list), so this is not a real risk in practice. Consistent with `toSrt` which also doesn't null-check. Author decides whether to add `Objects.requireNonNull` for fail-fast documentation.
- **Suggested fix:**
  Optional: `Objects.requireNonNull(cues, "cues")` as first line, matching Effective Java item 49.
