## C1 — Streaming write via `transferTo` satisfies no-buffer-the-whole-body requirement

- **Location:** `ThumbnailDownloader.java:74` — `body.byteStream().transferTo(out)`
- **Severity:** Praise
- **Category:** Readability
- **Reviewer comment:**
  Good use of `InputStream.transferTo(OutputStream)` — bytes flow from the OkHttp response body stream directly to the file output stream without buffering the entire response in memory. Consistent with `StreamDownloader`'s streaming discipline and the architecture's "heap footprint bounded independent of stream size" invariant.

## C4 — Reflection-based timeout verification in test

- **Location:** `ThumbnailDownloaderBehaviorTest.java:97` — `field.setAccessible(true)`
- **Severity:** Minor
- **Category:** Testing
- **Reviewer comment:**
  Using reflection to verify internal OkHttpClient timeout configuration is fragile — a field rename breaks the test silently. The `CaptionDownloader` tests (if they exist for the same concern) would have the same issue. A more robust alternative: call `create()`, then use `OkHttpClient`'s public getters directly on the returned downloader's client. However, since the field is `private final` and the class is `final`, the only access path *is* reflection or exposing a package-private getter. Acceptable for now; the test does verify the NFR-THUMBNAIL-DOWNLOAD-TIMEOUT = 10s contract.
- **Suggested fix:**
  Consider adding a package-private `OkHttpClient client()` accessor to `ThumbnailDownloader` for test use, eliminating the reflection. Low priority.

## C6 — Highest-resolution selection by width×height area

- **Location:** `ThumbnailDownloader.java:86–88` — `Comparator.comparingLong(t -> (long) t.width() * t.height())`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** T-4.8 task description ("pick max width × height thumbnail"), `02-architecture.md` § 1.2.2 ThumbnailDownloader
- **Reviewer comment:**
  Cast to `long` before multiplication prevents integer overflow for hypothetical very-large thumbnails (e.g., 4320×7680 = 33M, within int range, but the cast is a good habit). The `max()` comparator correctly selects the largest-area thumbnail. Test coverage confirms with 3-element and tied-area cases.

## C7 — Exception type consistency (NetworkException for all failures)

- **Location:** `ThumbnailDownloader.java:65,70,77`
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-5.2 (exit code 10 for network failures), `06-formal/cli-exit-codes.md` (ThumbnailDownloader listed under code 10 detecting components)
- **Reviewer comment:**
  All failure paths (HTTP non-2xx, null body, IOException, empty/null thumbnail list) throw `NetworkException`. This is consistent with `cli-exit-codes.md` which lists `ThumbnailDownloader` as a detecting component for exit code 10. The "empty list → NetworkException" choice is debatable (it's arguably a data issue, not a network issue), but it's consistent with the single-exception-type policy stated in the task brief and keeps the exception hierarchy simple. The architecture § 4.3 says thumbnail failure is non-fatal in combined flows — the orchestrator (T-4.10) will catch and WARN.

## C8 — Missing `Accept` header (unlike CaptionDownloader)

- **Location:** `ThumbnailDownloader.java:59–62`
- **Severity:** Nit
- **Category:** Readability
- **Reviewer comment:**
  `CaptionDownloader` sets `.header("Accept", "*/*")` on its request; `ThumbnailDownloader` does not. Both are functionally equivalent (OkHttp sends no `Accept` header by default, which servers treat as `*/*`). The inconsistency is cosmetic. No functional impact — YouTube's thumbnail CDN (`i.ytimg.com`) serves images regardless of `Accept`.
- **Suggested fix:**
  Add `.header("Accept", "image/*")` for explicitness, or leave as-is. Author's call.
