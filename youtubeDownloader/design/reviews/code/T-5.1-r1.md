## C1 — Missing WARN log when `--video` combined with `--audio-only` (AC-2.5 violation)

- **Location:** `Cli.java:171` (`computeEffectiveVideo()`) and `YoutubeDownloader.java:166`
- **Severity:** Major
- **Category:** Spec-Adherence
- **Spec citation:** AC-2.5: "IF `--audio-only` is combined with `--max-height` OR any other video-specific flag, THEN the system SHALL log a warning naming the ignored flag but SHALL NOT fail."
- **Reviewer comment:**
  `--video` is a video-specific flag. When the user passes `--video --audio-only`, the `computeEffectiveVideo()` method returns `true` (explicit override), but `YoutubeDownloader.download()` routes to `downloadAudioOnly` because `request.audioOnly()` takes precedence. The `--video` flag is silently ignored — no WARN log is emitted. AC-2.5 requires a warning naming the ignored flag.
- **Suggested fix:**
  In `Cli.call()`, after `computeEffectiveVideo()`, add:
  ```java
  if (audioOnly && Boolean.TRUE.equals(video)) {
      LOGGER.warn("--video ignored: --audio-only takes precedence (AC-2.5)");
  }
  ```
  And set `effectiveVideo = false` in this case so the `DownloadRequest` doesn't carry a contradictory `video=true, audioOnly=true` state.

## C2 — Contradictory state in `DownloadRequest`: `video=true` + `audioOnly=true`

- **Location:** `Cli.java:113–126` (request construction) and `DownloadRequest.java:37`
- **Severity:** Major
- **Category:** Correctness
- **Spec citation:** 04-apis.md § 3.1.2: "`--audio-only` … disables `--video` implicitly"
- **Reviewer comment:**
  When `--video --audio-only` is passed, the record is constructed with `audioOnly=true, video=true`. The spec says `--audio-only` "disables `--video` implicitly". The current code allows a contradictory state to exist in the domain record. Library embedders calling `new DownloadRequest(..., audioOnly=true, ..., video=true)` get undefined routing semantics — the orchestrator happens to check `audioOnly` first, but this is an implicit contract, not an explicit one. A compact-constructor validation or a resolution in `computeEffectiveVideo()` would make the contract explicit.
- **Suggested fix:**
  Either (a) add a compact-constructor check in `DownloadRequest`:
  ```java
  public DownloadRequest {
      if (maxHeight < 0) { throw ...; }
      if (audioOnly && video) {
          throw new IllegalArgumentException("audioOnly and video cannot both be true");
      }
  }
  ```
  Or (b) resolve in `computeEffectiveVideo()` by forcing `effectiveVideo = false` when `audioOnly` is true (and emit the WARN per C1). Option (b) is simpler and matches the spec's "disables implicitly" language.

## C3 — Test asserts wrong semantics for `--video --audio-only`

- **Location:** `CliVideoFlagBehaviorTest.java:83–86`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** AC-2.5, 04-apis.md § 3.1.2
- **Reviewer comment:**
  Test `execute_givenVideoAndAudioOnly_exitsZero` has `@DisplayName("--video --audio-only → exit 0 (explicit --video overrides audio-only implicit disable)")`. The display name claims `--video` overrides `--audio-only`, but the actual runtime routes to `downloadAudioOnly` — `--video` is the one being overridden. The test passes (exit 0 is correct — AC-2.5 says "SHALL NOT fail") but the display name is misleading. Once C1/C2 are fixed, this test should also verify the WARN log is emitted.
- **Suggested fix:**
  Rename to `"--video --audio-only → exit 0, WARN emitted, routes to audio-only (AC-2.5)"` and add an assertion on stderr containing the warning text.

## C4 — `computeEffectiveVideo()` does not account for `--audio-format mp3` implying `--audio-only`

- **Location:** `Cli.java:171–185` (`computeEffectiveVideo()`)
- **Severity:** Minor
- **Category:** Correctness
- **Spec citation:** AC-2.4 (mp3 implies audio-only), 04-apis.md § 3.1.2
- **Reviewer comment:**
  `computeEffectiveVideo()` is called AFTER the `--audio-format mp3` → `audioOnly = true` coercion (line 109–111), so the `audioOnly` check at line 178 does catch this case. The ordering is correct but fragile — if someone reorders the method calls, the default computation breaks silently. A brief inline comment noting the dependency on call order would help maintainability.
- **Suggested fix:**
  Add a comment above `computeEffectiveVideo()` call:
  ```java
  // Must be called AFTER --audio-format mp3 coercion sets audioOnly=true
  boolean effectiveVideo = computeEffectiveVideo();
  ```
