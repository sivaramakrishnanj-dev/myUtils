## C1 — DownloadContext.deleteRecursively fix: correct domain exception

- **Location:** `DownloadContext.java:113` — `deleteRecursively` lambda
- **Severity:** Praise
- **Category:** Correctness
- **Spec citation:** `cli-exit-codes.md` § 3 (code 70 → `FilesystemException`), INV-11
- **Reviewer comment:**
  The audit correctly identified that the `forEach` lambda in `deleteRecursively` previously threw a bare `RuntimeException` wrapping the `IOException`. This violated `cli-exit-codes.md` § 4 invariant 1 ("every non-zero exit corresponds to exactly one category") because a bare `RuntimeException` would bypass `ErrorMapper` and produce an undocumented exit code. The fix to `FilesystemException(message, cause)` is correct — the two-arg constructor exists, wraps the `IOException` cause, and `exitCode()` returns 70.

## C4 — Minor: `close()` catch block no longer catches the `FilesystemException`

- **Location:** `DownloadContext.java:93` — `close()` method
- **Severity:** Minor
- **Category:** Reliability
- **Spec citation:** INV-6 (.yt-tmp lifecycle)
- **Reviewer comment:**
  The `close()` method's `catch (IOException e)` block only catches checked `IOException`. After the fix, `deleteRecursively` throws `FilesystemException` (a `RuntimeException`), which escapes `close()` entirely. This means a deletion failure during cleanup now propagates to the caller rather than being logged as a WARN. The test confirms this is intentional behavior (the regression test asserts the exception escapes). This is acceptable — a filesystem failure during cleanup is a real error that should surface — but it changes the contract of `close()` from "best-effort cleanup" to "throws on cleanup failure when success was marked." The caller (`YoutubeDownloader` orchestrator) must handle this. Since the orchestrator already catches `YoutubeDownloaderException` at the top level and maps it via `ErrorMapper`, this works correctly end-to-end. Noting for documentation awareness only.
- **Suggested fix:**
  Consider adding a Javadoc `@throws FilesystemException` on `close()` to document the new contract explicitly. Not blocking.
