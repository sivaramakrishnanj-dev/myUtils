## C1 — AC-5.1 single-line error compliance: OBS-1 fixed correctly

- **Location:** `Cli.java:138` — `LOGGER.error(report.message())` (no Throwable arg)
- **Severity:** Praise
- **Category:** Spec-Adherence
- **Spec citation:** AC-5.1, OBS-1 in open-questions.md
- **Reviewer comment:**
  The root cause of OBS-1 was `LOGGER.error(report.message(), t)` — SLF4J-simple prints the full stack trace when a Throwable is passed as the second argument. ## C6 — Minor: `LOGGER.debug` in catch block produces duplicate stack trace in --debug mode

- **Location:** `Cli.java:140` — `LOGGER.debug("Stack trace for above error:", t)`
- **Severity:** Minor
- **Category:** Observability
- **Spec citation:** AC-10.4 ("emit at ERROR level exactly once per failure")
- **Reviewer comment:**
  When `--debug` is active, the stack trace appears twice on stderr: once via `LOGGER.debug(...)` (SLF4J-simple prints it) and once via `t.printStackTrace(err)`. AC-10.4 says "exactly once per failure" for the ERROR-level message (which is correct — only one `LOGGER.error` call). The DEBUG-level trace is technically a different level, so this is not a spec violation. However, the user sees the stack trace printed twice to the same stream, which is noisy. Consider removing the `LOGGER.debug` line and relying solely on `t.printStackTrace(err)` for the user-facing trace — or keeping `LOGGER.debug` but removing `t.printStackTrace(err)` and relying on SLF4J's output. Either way, one path is sufficient.
- **Suggested fix:**
  Remove `LOGGER.debug("Stack trace for above error:", t);` — the `t.printStackTrace(err)` already writes to stderr, and the picocli err writer is the correct output channel per AC-5.5.
