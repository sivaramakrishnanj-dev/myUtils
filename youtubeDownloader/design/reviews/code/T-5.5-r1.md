## C3 — `InnerTubeClientRequestShapeTest.fetchPlayer_bodyMatchesFixtureShape` — semantic preservation after metadata addition

- **Location:** `InnerTubeClientRequestShapeTest.java:174–181`
- **Severity:** Praise
- **Category:** Testing
- **Spec citation:** CT-REQ-1, AC-12.1
- **Reviewer comment:**
  The test correctly moved from full-equality (`assertThat(actual).isEqualTo(expected)`) to field-by-field comparison (`videoId`, `context`, plus `actual.size() == 2`). This preserves the semantic intent — the request body must match the fixture's *request shape* — while correctly excluding the `x-captured-on` metadata field that exists only in the fixture file, not in the actual request. The `size() == 2` assertion ensures no accidental extra fields leak into the request body. Clean adaptation.

## C4 — `FixtureMetadataTest` validates parser transparency for all response fixtures

- **Location:** `FixtureMetadataTest.java`
- **Severity:** Minor
- **Category:** Testing
- **Spec citation:** ADR-0004 (`FAIL_ON_UNKNOWN_PROPERTIES = false`)
- **Reviewer comment:**
  The test covers 6 response fixtures but omits `innertube-request-happy.json`. This is correct — `PlayerResponseExtractor` only parses *response* fixtures, not request fixtures. The request fixture's `x-captured-on` transparency is implicitly covered by `InnerTubeClientRequestShapeTest.fetchPlayer_bodyMatchesFixtureShape` (which loads the fixture and compares field-by-field, ignoring the metadata). No gap here, but the test's `@ValueSource` comment could note why the request fixture is excluded for future readers.
- **Suggested fix:**
  Optional: add a one-line comment above `@ValueSource` — `// request fixture excluded: PlayerResponseExtractor does not parse requests`.
